# Verification, review, and automation in Morpheus

November 17, 2026 · Evidence and proposed experiments

Morpheus already uses many of the practices Anthropic describes. Its independent reviewer is a fresh session, substantive findings have dispositions, reviews cover concrete commits, and product teams already use browser, simulator, physical-device, and replay harnesses. The gaps are more specific. A candidate can influence the policy used to judge it. A passing stage can stand in for a user-visible outcome. Worklogs preserve useful failure cases, but the current measures cannot tell us which reviewer would have caught past escapes.

**Start with two small changes in separate follow-ups.** Fix the ownership of review policy using a trusted base. Then pilot one short Evo journey and check how Darwin's Operations Desk presents delivery evidence. Run the review evaluation and automation replay in shadow mode before changing review budgets or adding gates.

## Ranked improvements and experiments

Ranking weighs blast radius, direct evidence, and the cost of getting a decisive result.

### 1. Move review policy to the trusted base

**Evidence.** A disposable Git repository with a substantive change and missing review initially returned exit 1. The same CLI returned exit 0 with an independent-review waiver when the proposed change also relaxed project policy. Morpheus also compiles and runs its own candidate conventions checker in CI to verify workflow and CLI changes. That is valuable candidate coverage and should be preserved alongside a trusted merge decision. The synthetic probe exercised the CLI locally. It establishes neither a hosted bypass nor the state of deployed protections in every consumer. [Morpheus CI](../../.github/workflows/ci.yml#L178-L206) · [Reusable PR check](../../.github/workflows/pr-check.yml) · [Review policy](../../docs/runbooks/independent-review.md#policy)

**Experiment.** Start with a repo-local comparison of the current decision and a decision using a pinned base checker and base policy, each reading evidence and changed files at the actual PR head. Exercise ordinary code, legitimate policy tightening and relaxation, initial opt-in, already opted-out projects, a stale head and missing base data. Validate any intentional relaxation under the current trusted policy and give the policy change its own explicit review. Keep candidate-checker tests to catch upgrades that the previous version cannot understand. Before enforcing, define how a reviewed schema or waiver transition can ship when an older checker cannot read it.

**Pass.** The synthetic weakening case is refused, every established intended exception still reports correctly, and no ordinary unchanged-policy case changes its verdict on a 20-PR replay. Review every disagreement and measure the added required-check time before choosing where to run the comparison. The merge authority belongs in a protected GitHub rule or independently governed check if the project can also change its workflow. Use a named owner to approve relaxations to required review or comparable release and authorization controls. Leave the ordinary risk-tiered route available for product changes.

### 2. Pair a short Evo journey with Darwin delivery-evidence checks

**Evidence.** Evo's release and review records distinguish source, native evidence and delivery. Darwin's operator-verified dashboard contract was built using synthetic browser states, which are well suited to fast checks. Morpheus already recommends testing observed effects and assigns closure to the verified downstream receipt. [Release ownership](../../docs/runbooks/pm-workflow.md#what-a-pr-carries) · [Infra dashboard verification](../../docs/runbooks/infra-dashboard-design.md)

**Experiment.** Give the Evo iOS owner one command against a disposable simulator and synthetic data. Capture a fixture meal, wait for analysis, save, relaunch, and assert the persisted result and single save. Return the first failed step, selected test output, exact source/build identity, and a screenshot or trace when useful. Separately drive the existing Darwin browser fixture through current attempt → failed or pending confirmation → confirmed result, plus an unreadable source. Check the same source identity and receipt class through the scoped view. Take physical-device and service-boundary evidence from the existing release process for the risks that require those environments.

**Pass.** Detect a seeded save/persistence break and a stale/failure rendering error. Run 20 clean seeds across a warm and fresh environment and accept at most one unexplained failure before expanding. Target a warm p90 within five minutes and preserve time-to-first-failed-step. Start on meal capture/persistence and Operations Desk changes where the checks answer a specific question.

### 3. Turn worklogs into a review evaluation with real controls

**Evidence.** A scan of Morpheus main at `b7ebe5c7` found 228 distinct reviewed/covered SHA pairs in dated worklogs from October 15 through November 17. Of those, 112 record a substantive finding and 98 have a follow-up. Landed worklogs provide material for replay. Estimating reviewer precision or escape rates requires a separate denominator and adjudicated outcomes. October profiling found Evo review-coverage failures rising from 6 to 14 in its sampled windows. Work on pre-push evidence and on model/effort evaluation is already filed. [Profiling and correction](../../.agent/worklog/2026-10-28-profiling-round-2.md) · [Pre-push work](../../hq/product/roadmap/MO-26-10-28-14.11.06-cut-post-review-churn.md) · [Existing replay proposal](../../hq/product/roadmap/MO-26-10-28-14.11.05-benchmark-model-effort.md)

**Experiment.** Start with six historical problem diffs and six matched stable diffs across the four focus projects. Prefer incidents and fix-forwards for escapes, with selected pre-merge findings labelled separately. Freeze the exact historical tree, toolset, and one-sentence answer key. Withhold the fix and later records. Use a small disjoint tuning set. Compare the existing reviewer with the same reviewer using a few trusted-base, diff-triggered checks tied to recorded incidents. Have a domain owner judge blind to the arm. Record whether a finding was surfaced, reproduced, and retained, its severity, tokens, first actionable finding time, follow-up count, and owner time spent. Repeat one small subset to gauge run-to-run noise.

**Pass.** For this pilot, recover at least one additional known important defect, retain every baseline high-impact hit, and produce zero harmful must-fix claims on stable controls. Report raw counts and repeated-run variance. Expand the holdout before drawing fleet conclusions. Feed repeatable mistakes into scoped guidance or a deterministic test. Use the current author-managed reviewer and GitHub Manager roles for live delivery.

### 4. Show receiver and delivery health in the existing Operations Desk

**Evidence.** The portable scheduler already reconciles duplicate and uncertain dispatches. It explicitly treats a red receiver run as receiver health, and there is an existing proposal for unowned failed CI. The desk already distinguishes stale, unknown and failed observations. The missing join is an expected occurrence, the receiver's outcome, and the independently confirmed effect. [Scheduler health](../../docs/runbooks/scheduler.md#status-and-health) · [Unowned run triage](../../hq/product/roadmap/MO-26-10-28-14.11.00-triage-unowned-ci-failures.md) · [Dashboard design](../../docs/runbooks/infra-dashboard-design.md)

**Experiment.** Shadow one enrolled job in Darwin's existing read model, using its existing transport and writer. Use the occurrence or source identity, last attempted observation, last successful observation, and a terminal receipt or a visible unknown reason. Replay a delayed receiver, source denial, expiry, duplicate trigger, crash after provider success before local acknowledgement, and a successful no-op. For data intake, keep the unreadable source's checkpoint, reread current preferences, and reconcile a stable destination identity before moving its delivery ledger. Make missed runs visible through an observer outside the job being monitored. Keep project-level actions with their existing owners.

**Pass.** Every replayed degraded state is surfaced within one observer cycle. No false green, lost item or duplicate effect. A repeat uses read-only reconciliation before any authorized retry, and old confirmed success keeps its original age. Once a second project needs the same receipt semantics, decide whether to extract a shared helper.

### 5. Extend Lakina's offline execution and accounting replay

**Evidence.** The prior Lakina audit killed 30 of 48 mutants despite 87% line coverage. That was a historical audit with a deliberately small mutation set. Its strongest transferable result is the benefit of asserting exact financial values and recovering ambiguous external outcomes by identity. [Test-quality runbook and audit pointer](../../docs/runbooks/test-quality.md)

**Experiment.** Use the existing replay harness and synthetic cases. Generate seeded permutations of duplicate and reordered fills, rounding boundaries, lease loss, timeout before or after provider acceptance, and crash before receipt persistence. Assert exact cash/positions/fees under a simple independent arithmetic oracle, stable intent identity, and no second submission when the first outcome is ambiguous. For compatibility changes, compare approved and candidate executors on the same traces, normalizing time and opaque IDs with a short list of intentional differences. Preserve a failed seed as a named fixture.

**Pass.** Catch three deliberate regressions in the sampled paths: duplicate fill accounting, a rounding error, and repeat submission after an ambiguous acknowledgement. The unchanged harness passes all selected seeds, and the candidate never gains execution authority in the replay. Compare run time and coverage of failure modes with the existing named cases before adding dependencies or CI time.

### 6. Rehearse recovery at the artifact boundary

**Evidence.** Release preflight, scoped incident ownership, and protected CI are established. A release can still fail after the merge and the tests. A code revert, workflow rollback, stopped promotion, and an already installed iOS build each have different recovery semantics. [Release workflow](../../.github/workflows/release-preflight.yml) · [Incident ownership](../../docs/runbooks/pm-workflow.md#what-a-pr-carries)

**Experiment.** Walk one synthetic failed canary each for a shared Morpheus workflow and an Evo release, or an authenticated web deploy where a previous artifact can be selected. Use the current owner, exact last-good artifact, conditions for defensible recovery, and a caller-side verification probe. For installed iOS clients, practice holding promotion and validating the forward repair and supported client contracts. For Lakina, exercise disabling the affected paper lane and reconciling its last outcome offline.

**Pass.** Identify the correct recovery action and owner within ten minutes of injection, verify the returned user-visible state on the expected artifact, and retain the failed attempt. Use the time and evidence to decide where to add an automatic probe or a release flag.

## Validation and limits

Ran the synthetic Morpheus CLI comparison and 353 focused PR-check, local-review, scheduler and intake tests. Read and sampled worklogs at pinned Git revisions, checked the public source links, and ran selected Evo pipeline-contract, Darwin component and Lakina replay/registry checks. Those tests exercised repository contracts and local fixtures. Live device delivery, production recovery, and provider-side mutations were outside this audit. The recommendations are experiments with success criteria. Their effect on review quality and release reliability remains to be measured.
