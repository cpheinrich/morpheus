# Morpheus Context and task efficiency audit

**Recommendation:** keep Markdown in Git, keep Context MCP for project records and codebase-memory for structural code. Fix the read interface and worktree attribution first, then test whether it gets agents to correct evidence and operators to accepted outcomes sooner. There is measured tool-level progress. There is no causal estimate of end-to-end speed, operator leverage or shipping acceleration yet.

Scope: November 8–15, 2026 UTC, based on public release and worklog evidence, a privacy-filtered desktop sample through 13:21 UTC on November 15, and one readable secondary host. The three consuming projects include app, web, and infrastructure work; their observation rows are anonymous. No private record text, prompts or underlying log rows are in this audit. The [companion analytics draft](https://github.com/cpheinrich/morpheus/pull/715) specifies the two-week pilot and exact denominators.

The 395 logged MCP searches include 394 `ok` and one error. There were 101 CLI searches, 66 Claude augmentation-hook searches and 95 traces without reliable transport attribution. Nonempty does not mean the result answered the question, and some failures can occur before trace creation. The larger cohorts returned a median of roughly 1,000–1,200 estimated tokens. About 11.2% of **logged** exact reads were errors (78/697); exact read median was 74–96 ms across the three larger projects. An exact read can fail before evidence is seen; its error reasons aren't in the v1 trace. This is a larger observed friction signal than logged query errors. A separate Codex transcript check confirmed that range and coverage errors occur on real calls; host transcript and server-trace samples cannot be pooled. A default read covers 16 lines even with a larger token cap. A range over 100 lines is refused. These can be demonstrated from tool source and readback, but we cannot attribute all or most historical errors to them. The trace calls out partial results but [the current rollup parser](../src/context-search/trace-summary.ts) drops that flag.

To check direction after the performance work, split at #695 and #696 merge clocks and exclude the short interval between. Project A's median moved **575 → 366 ms** (41 / 119 searches) while p95 changed **2.82 → 3.00 s**. Morpheus's median was **393 → 393 ms** (53 / 75) while p95 moved **1.56 → 1.20 s**. C's median changed **489 → 367 ms** (16 / 66) while p95 increased from **0.80 to 2.40 s**, with a thin early tail. Cache hit fractions and call mixes changed. These comparisons are chronological, not attribution to a build. The server advertises the same MCP version across these changes; Git merge time is not installation or process restart. Don't report a universal improvement or a regression from this split.

These are observable call counts, with no denominator of sessions that needed a record or a structural lookup. Main/reviewer/subagent reflect transcript classification; receipt-matched Factory sessions are shown separately regardless of transcript role. An unmatched Factory session may still land in another bucket. A worker's many calls do not make it many users. CLI fallback and Claude hook evidence can complement direct usage and must be kept separate. No observed graph call in a small Claude bucket does not prove the graph was absent or unused fleet-wide. Registration is not health. In a strict literal-project-name transcript subset (not the normalized session table), Codex's `search_graph` median/p95 were 49/153 ms (246 spans); `trace_path` 15/42 ms (116); and coverage 10/17 ms (283). In that same subset, Context search client spans were 394/3,007 ms (470 Codex) and 472/3,700 ms (19 Claude). These calls answer different questions and can't establish a speedup over grep. Some client-side calls have no corresponding eligible trace in the local subset. Nearby root facilities can emit duplicate or parallel tool records; elapsed session time is not the sum of spans.

**Work and time:** 417/657 search events joined to a profiled session on the same project using the existing rollout-scoped hash; 208 had an identifier but did not match, and 32 were unattributed. This provisional join rejected cross-project conflicts and did not assign an unknown trace to a provider on the basis of latency. 124 local Factory run records were in scope, but only 51 profiled sessions matched a run; run and session counts have different grains and resumed runs may share a session. Many author/reviewer transcripts lack a task ID, and review and deployment touchpoints are not acceptance. The secondary host's alternate installed CLI supported context profiles, but found no context-trace activity across these four local checkout families. Its default PATH CLI lacked the profiling command. This shows a sampling/installation gap; no conclusion about that host's usage or Fleet follows.

There is a viable downstream surrogate for some work. For four public Morpheus changes with a retained claim commit and delivery timestamp, claim → merge was **18.6, 21.5, 22.7 and 13.0 min** for #695, #696, #706 and #709, respectively. The corresponding PR-open → merge times were about **10.9, 10.6, 19.5 and 10.9 min**. These are selected shipped PRs. The clock excludes intake before claim and stops at merge, and the intervening wall time is not operator time. The current profile can expose elapsed time, approximate active agent time, requests, spans and tokens, but it cannot say how long a human spent briefing, steering or validating. It cannot tell whether this search layer reduced overall task time. This example is enough to prove the pipeline pieces exist, not enough to prove acceleration.

**Records as a product surface.** We checked tracked meeting-note Markdown eligibility in three consuming projects (1, 8 and 12 eligible, none unavailable in that path at the sampled checkouts), as well as rollout worklogs and their links to decisions/roadmap. Meeting catalogs can be discoverable even when the underlying authorized source material lives elsewhere. An indexed heading, an inventory count and a path match are not proof of a governing decision or complete capture. The high-value future behavior is an evidence trail across meeting → decision → roadmap → acceptance. Keep decisions authoritative in Git and preserve the distinction between links, cited source, and judgments about relevance.

**Local transport probe (development only).** On a newly cloned public checkout at `db0231bd`, a first stdio search immediately after MCP initialization took **1.81 s** (launch/initialization itself not timed). The resident server then answered 24 requests at **129 ms p50 / 140 ms p95** versus **549 / 563 ms** for 24 paired one-shot CLI requests on the same warm corpus. All 24 pairs favored the resident transport; median paired difference was **417 ms**. Both transports found the expected file on **5/8** distinct information needs in each of three repeat passes. Two misses concerned warm-index/reviewer guidance and one concerned source discovery. A file match is weaker than a correct evidence span; this is a handpicked, exposed dev set, not a holdout or a comparison against ordinary agent search.

Cases (expectations frozen before running): source globs and main reuse → `2026-11-12-speed-context-search.md`; edits during rebuild → `2026-11-12-rebuild-context-index.md`; Claude Grep/pending approval → `2026-11-09-wire-context-search-hooks.md`; compact receipt recovery → `2026-11-14-standardize-compact-startup.md`; profile roadmap ID → `MO-26-10-07-20.55.11.md`; original warm Tantivy timings → `2026-11-07-context-search-rollout.md`; launch warming before prompt → `2026-11-09-warm-context-index.md`; author Suggested context → `independent-review.md`. Timing starts just before sending each request (or spawning CLI) and stops after parsing JSON citations. Both use a 1,000-token return budget; stdio call `search_project_context` versus `morpheus context search --max-tokens 1000 --json`. Three passes alternate pair order with a fixed seeded query order. Use a disposable clone to separate cold startup from an already indexed checkout.

## Ranked proposals

Effort is an engineering estimate including verification; impact is relative to **operator time and correctness**, not call throughput. The ranges below are scenario math to test, not measured lift. For the exact KPI definitions and data windows, see the companion operator-leverage pilot.

| Rank | Change | Expected impact / effort | Confidence / sequence |
|---|---|---|---|
| 1 | Make failed reads and partial results recoverable in one turn. | Medium to high / 1–3 days | Two causes reproduced; add reason codes first. |
| 2 | Fix worktree attribution and baseline the existing evidence by build and role. | High decision value / 2–4 days | Attribution defect reproduced; start in parallel with rank 1. |
| 3 | Test the actual host/role path; replace duplicate work selectively. | High if misses cluster / 2–4 days | Moderate; verify one host and role at a time. |
| 4 | Establish transfer to correct decisions and accepted work. | High decision value / 3–7 days plus sampling | High need, unknown effect size. Do before further investment in ranking. |
| 5 | Carry the evidence forward in work and review handoffs. | Potentially high / 2–5 days | Moderate; begin manually with one workflow. |
| 6 | Surface sporadic tail costs or defer optimizing them. | Low typical, potentially high tail / 1–3 days to diagnose | Moderate; do only on a repeated, attributable bottleneck. |

1. **Read contract and partial fallback.** Bucket errors into coverage, out-of-range, unavailable and unknown before tuning ranking. Accept local heading anchors or supply exact `path/from/to` read parameters in overview; avoid fetching external architecture URLs as part of record reads. Add an explicit continuation boundary and next step when range is too broad or content truncated; keep the 16-line default and budget until evidence suggests otherwise. Audit error recovery via one known record outside the corpus and one just edited. Preserve out-of-corpus refusal and partial-empty warnings. If a quarter to half of the observed 78 errors are avoidable in a comparable period, that is roughly 20–39 failed attempts removed; every 5–20 s of avoided follow-up per recovered attempt is about 2–13 min of aggregate agent elapsed time. Human saving is unknown unless the issue required a person. Roll out a reason field and hint first; watch retries, safe fallback and erroneous absence claims.
2. **Attribution and operator leverage pilot.** First correct repo attribution for task worktrees and Factory slots with tests on their actual layouts; prefer authoritative Git/receipt identity when available. Reuse `context profile`, provider transcript spans and Factory receipts. Add executing build, cache/partial/error reason, and local task/attempt correlation; export aggregate scorecards only after coverage is understood. Start with today's one-host data, then opt into two projects for two weeks. Test local joins against known linked/resumed/fresh cases, and leave missing IDs unknown. Target ≥90% attributable pilot attempts. Capture a small human-time sample and a separately evidenced acceptance timestamp. This mostly reduces decision uncertainty; it cannot by itself be reported as operator hours saved. Cut the new export if it cannot preserve the privacy boundary or exceeds the agreed overhead.
3. **Role × client × checkout smoke matrix, followed by a small nudge comparison.** Prove the same known record is searchable and readable on Codex root/reviewer/subagent, trusted Claude root/subagent, and actual Factory checkout. Separately use a tiny code graph with expected caller/coverage behavior, and probe missing graph plus stale scope. Add a real Claude MCP hook payload fixture and verify receipt credit with an observed positive control before claiming a gate defect. Try omitting unneeded orientation calls for a known path. Where Claude Grep augmentation is followed by a redundant MCP/prompt turn, compare current vs a hint-only or direct-MCP-first variant on that client. Do not disable direct shell fallback or add a startup gate. Example: on a stale or misbound project the MCP can query a default scope; an overview can show project but the same repo name cannot disambiguate two worktrees. Use scope identity validation, not tool presence. If 10–30% of 100 eligible episodes avoid one 10–30 s retrieval cycle, the scenario is ~2–15 aggregate agent minutes, potentially more if it prevents a wrong implementation. Change the default only when advice removes net work without reducing source or acceptance correctness.
4. **Pair replay by task, not by logs.** Use real frozen lookups and small historical decision/tasklets: exact IDs, descriptive precedent, strict citation, missing/unavailable records, stale index, conflicting/superseded advice, and structural coverage. Compare ordinary grep/read/graph vs the same tools plus current MCP, and isolate compact startup in a separate factor. Start with twelve diverse dev cases. Freeze permission, model/effort, corpus revision, roles and cache states; counterbalance order and keep an unseen group held out. Blinded scoring: correct decision, evidence span, time to first sufficient evidence, next-action correctness; track follow-up calls, tokens and human interventions. A practical pilot bar: ≥20% lower median time to sufficient evidence or one fewer retrieval turn, with no severe grounded decision regression. Report exact boundary and uncertainty; skip a larger run when measurement noise would dominate.
5. **Evidence handoff for the next worker and next task.** Build on `get_related_context` and `review prepare`, not a second knowledge base. Carry at most a few source ranges, revision or stable heading, the recorded decision including supersession, and what remains unverified. Try one human intake → Factory → reviewer → acceptance flow. Compare repeated retrieval and missed policy, with each reviewer verifying the evidence rather than inheriting the author's conclusions. One avoided context-correction loop that costs a human 4–12 minutes on 1 in 10 similar tasks would save 0.4–1.2 min of human time per task; sample before expecting a lift. Keep relation changes advisory; drop auto-suggestions if they promote stale decisions or repeat history already in the handoff. Low invocation volume for `get_related_context` is a reason to validate this flow, not enough on its own to remove the tool.
6. **Tangential owner opportunity: profile the ritual before adding a new system.** Separate queue, review, CI, session startup/claim and retry spans. A fast call may be irrelevant if opening the task, certifying read evidence or routing the worker takes longer. This audit needed a bounded re-read because oversized output did not count toward the receipt; narrowing the terminal read provides evidence today. Make `context refresh` show next actionable bounded reads and missing provider ID early. Retain the actual freshness invariant. Profile worktree enumeration before suggesting cleanup; age alone proves neither abandonment nor cost. For tool latency, use cache-hit/miss, snapshot-fingerprint and I/O attribution before chasing p95: 20 calls × 0.2 s = only four seconds of direct savings, even if all are on the critical path. Defer new indexing engines, a hosted store, and fleet-wide policy changes until the pilot shows who needs them.

## Reproduction and limits

- Baseline: reviewed public trunk `db0231bd` and the release worklogs linked above. Use `git log --first-parent`, `gh pr view … --json createdAt,mergedAt,commits`, and tagged worklogs for deployment dates, matching claims and recorded pilot results. Join to release or acceptance evidence explicitly; do not infer it from merge.
- Diagnostic logs: `morpheus context profile 2026-11-08` from each checkout and `morpheus profile extract --since 2026-11-08 --out <private-path>`. For the audit cut, filter version-1 JSONL with `2026-11-08T00:00:00Z <= at < 2026-11-15T13:21:00Z` across local worktrees and Git metadata archives, deduplicate identical rows per project, separate operations and transport, and use nearest-rank percentiles. Validate paths, archive duplicates and skip unsafe files. Server timing is `queryMs`; p95 includes captured failures. Fleet receipts cannot substitute for host-side tool attempts. `morpheus profile extract` reported six skipped malformed lines in the full host extract, outside the primary date window by file date; do not assume all parsers see all events.
- Join: recompute the existing rollout-scoped hash (`sha256("morpheus-context-v1\\0" + rollout + "\\0" + sessionId)`, hex chars 8–23 zero-indexed) locally; check project; retain unmatched. Identify Factory sessions from exact run receipt links. Resolve repository by registered worktree, then recognized name/layout; archive ambiguities stay outside the subset. Some new `morpheus-worktrees` layouts resolve to a task basename in the existing profiler, so do not rely on `--repo` alone. For weekly repeatability, prefer a proper task join over expanding path heuristics.
- Graph evidence for telemetry was scoped to the base checkout and relevant paths. Exact trace parser and dispatcher caller were inspected; best-effort coverage showed no recorded issues on those files. This is a narrow code audit, not an assertion about complete graph coverage in projects.
- Below the privacy boundary, keep one immutable extraction, aggregate script and manifest per cut. Saved local extracts contain commands and file paths and are excluded from the PR. Codebase-memory evidence, latency traces and related worklogs have different coverage and should remain separately sourced.

## Independent Factory audit

A fresh Claude Fable 5.2 worker ran through the Claude gateway in the claimed worktree. It reproduced the read failures and repository misattribution, then checked different denominators over a slightly later cutoff. Preserve the two samples separately.

- On the same host, its all-project transcript pass found **2,747 Context MCP spans**. Summed observed tool time was 14.5 minutes versus 155.7 estimated agent-active hours (~0.16%); the observations overlap in some parallel sessions and the ratio is a rough scale indicator. Coverage and overview accounted for 465/2,747 calls; related context for 2. Neither implies those calls were unnecessary. The ordinary shell search and model turnaround they might replace still matter.
- Its sample found **36/277** Morpheus exact reads flagged as errors, with 14 followed immediately by another failed read. It reproduced the `architecture.md#73-the-work-loop` rejection and the 100-line limit. The controller reproduced both failures and a successful plain path + numbered span. A separate sample of Codex result envelopes confirmed actual coverage and range failures; the share in the original server trace is still unknown.
- The profiler treats the task directory name as the repo with the **current undotted** `morpheus-worktrees/` layout, while the old dotted fixture succeeds. Factory slot names can also stay unresolved. Fable's host-wide normalization flagged 75/334 session rows; the controller verified current and legacy examples with the compiled `deriveRepo`. Treat the reported 22% as a sample estimate, not a fleet frequency.
- Fable's local join found **0 visible events for 14 successful Claude calls versus 266 for 336 Codex calls**, and no seen marker for its own three successful searches. The source has a Codex-specific branch for structured excerpts. Hook trust, message shape and identity could all affect this. The gate consequence is **unverified**; reproduce with a native Claude hook payload plus a positive control before changing the receipt logic. Do not equate this missing observation with an unseen result.
- Fable suggested making path/line reads easier, fixing repo attribution, verifying Claude receipt credit, then measuring setup and lookup ceremony. The controller kept the relationship tool and ordinary fallback through the pilot: low usage and a fast server don't establish that removing either is safe. No runtime changes or telemetry collection are enabled by this draft.
