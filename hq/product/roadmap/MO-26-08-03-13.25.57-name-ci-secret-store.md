## Context

`architecture.md` §13.1 said **two stores**: GSM for what code reads, 1Password for what a human
reads. CI was folded into "code", so GitHub Actions secrets were described as a delivery surface —
a cache of GSM kept aligned by `morpheus secrets push --ci`.

That command does not exist and should not be built. **For a secret only CI reads, the sync's source
and destination are the same place.**

I had proposed recording the Anthropic key's presence in GitHub as a *deviation* from the spec.
Chris rejected the framing: *"we will always use github secrets for keys needed during CI — why not
just make that a named default?"*

He is right, and the reason is the mirror of a rule already in `decisions.md`: **a deviation nobody
recorded is indistinguishable from the canonical choice.** The inverse costs just as much — a
canonical choice recorded as a deviation manufactures phantom work. A future agent reads "deviation"
and builds the sync to close a gap that is the design.

## Approach

Rewrite §13.1 around **who reads the secret**, with three readers rather than two:

| Store | Read by |
|---|---|
| Google Secret Manager | the deployed software |
| **GitHub Actions secrets** | **CI, and only CI** |
| 1Password | a human |

This is the same axis the section always used. The original just collapsed two of the three readers
into one, because at the time nothing in CI needed a secret.

Three things recorded alongside it, all of which were true and unwritten:

- **Workload Identity Federation is deliberately not used.** It would let CI reach GSM with no
  stored credential; it costs a pool, provider, service account and IAM binding per project plus an
  auth step in every workflow, to remove one encrypted value from GitHub. Not worth it at one CI
  secret and one operator — and worth revisiting only when CI needs a secret the runtime also reads.
- **The boundary case has a rule.** When CI and the runtime need the same capability, GSM owns it
  and CI gets its *own* credential, narrower. Two copies of one secret is what to avoid; two
  credentials for one capability is what to want.
- **`morpheus secrets pull` is specified but not built.** A command named in the architecture reads
  as a command that exists.

Also notes the consequence that decides where a secret may be used at all: **GitHub does not pass
secrets to `pull_request` runs from forks**, so a CI secret is unavailable on exactly the pull
requests external contributors open. Rung 2 reports itself unconfigured there — honest, but it
means outside contributions get no agent review.

## Test plan

Documentation and a decision record; no runtime code, so nothing to unit test. Verified by
`pnpm typecheck && pnpm test` staying green (561), `pm validate`, and `pm index --check`.

## Open questions

None. The fork consequence is stated rather than solved — solving it means `pull_request_target`,
which runs untrusted code with secrets in scope and is a much larger decision than this item.
