## Context

The reviewer delivers everything as one long tracking comment. Chris's call, 2026-08-18: findings
should land as **inline comments on the lines they are about**, where GitHub shows them against
the code and threads replies per finding — a block of prose citing `file:line` makes the human do
the join by hand, one finding at a time.

The capability already exists and is already permitted: the action exposes
`mcp__github_inline_comment__create_inline_comment` and the workflow allowlists it. What routes
everything into the block is the **persona's own "How to report" section**, which says "post a
single review comment" and calls inline comments "the exception". This is a prose change to the
personas, not a code change.

## Approach

Rewrite "How to report" in Morpheus's persona (Evo's mirrors it in its own PR):

- **Findings go inline**, each on the line it is about, self-contained, with the concrete
  input or state that breaks.
- **The tracking comment becomes the verdict**: a short summary listing each finding as one
  `file:line` line, anything that applies to no line in the diff (missing tests, scope,
  contradicted decisions), and the delivery sentinel.
- **A finding about a line outside the diff** goes in the tracking comment — the inline tool can
  only anchor to the diff, and asking for the impossible produces either silence or a misplaced
  comment.

Nothing downstream changes shape. `assessReviewDelivery` requires a substantive tracking comment
with the sentinel — the verdict satisfies it. The re-review gate reads file mentions from the
tracking comment — the summary's `file:line` list preserves them.

## Acceptance

- A review on a real pull request posts its line-anchored findings as inline comments and a
  tracking-comment verdict that names each finding's `file:line`.
- The delivery job still confirms delivery on that run.
