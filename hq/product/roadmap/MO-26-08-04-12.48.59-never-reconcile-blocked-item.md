## Context

`morpheus pm claim` marked four **blocked P0** items `shipped` in a downstream project, as a side
effect of claiming an unrelated item, reported as a single dim line.

`claim()` calls `reconcile()` before branching (`src/pm/claim.ts`). `reconcile()` selected
candidates with `status !== "shipped" && status !== "dropped"`, so `blocked` was reconcilable in
both write paths:

- **the claimed-branch path**, which is the one that fired: `pm claim` deliberately leaves a blocked
  item's branch on origin so its partial work stays reachable, and `claim()` says so in a comment.
  `reconcile()` then read that surviving branch plus its merged PR as `stale` and wrote `shipped`.
- **the unclaimed path**, where `backlog` was explicitly protected and `blocked` was not.

`backlog` was protected because a merged PR against it "may have been deliberately reopened".
`blocked` has the stronger claim: `pm block` records the outstanding work in `needs:`, so a merged
PR and an unfinished item are *both true at once* by construction. The merged groundwork is the
expected state, not evidence of completion.

**Why P1 rather than cosmetic.** The affected items gated a paper-trading kill switch, ambiguous
broker outcome recovery, a risk policy awaiting a human signature, and build provenance. One's
`needs:` ends "do not approve or activate execution before both". `ship.ts` already warns that a
shipped item is never looked at again — here that would have retired four safety gates on the
strength of their own groundwork PRs. The project had been fighting this by hand, with a commit
literally titled "Keep paper risk policy work blocked".

The `didNoWork` guard added after MO-010 does not cover it: these PRs did change source, so they
are real work. The point is that the work they did was never the whole item.

## Approach

Add a `blocked` outcome kind, reported and never written, in both write paths. Print it in the
warning colour with its `needs:` text and the `pm unblock` remedy — the original failure was as much
about a dim one-line summary as about the write itself.

## Acceptance checks

- A blocked item with a merged PR is reported, never written, whether or not its branch survives.
- The report names `needs:` and the command that clears the blocker.
- `backlog`, `review`, `no-work` and `stale` behaviour is unchanged.

## Implementation outcome

- `ShipOutcome` gains `{ kind: "blocked"; id; pr; needs? }`.
- Guarded the claimed-branch path before the `stale` branch, and the unclaimed path beside the
  existing `backlog` check.
- `formatReconcile` prints blocked items in yellow with `needs:` and the `pm unblock` remedy.
- Verified against the original reproduction: `morpheus pm ship --check` in the affected project now
  reports all four with their `needs:` and writes nothing.
- 592 tests pass, typecheck clean.

**Not covered by test:** `reconcile()` itself has no existing harness — it shells out to `gh` through
`mergedPrs()` and is not injectable, so the repository's own tests cover `markShipped`, `didNoWork`
and `formatReconcile` only. The new test follows that convention. Making the outcome decision a pure
function would close the gap and is a larger change than a first outside contribution should make
unasked.
