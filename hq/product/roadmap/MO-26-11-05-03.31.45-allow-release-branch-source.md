## Context

Evo's CD is getting branch-first releases. Chris (2026-11-05): *"create a release branch off of main
once staging CD starts and then we only merge fixes to that release branch, and then we merge the
release branch back into main once CD is complete."* After that, a repair candidate B sits on a
protected `release/ios-*` branch that `main` does not yet contain.

Today `release-preflight.yml` accepts only one of two sources, both checked as the run's own commit:
- the current `main` head; or
- with `allow-pinned-source`, a reviewed merged PR into `main` that `main` contains.

Neither accepts B. The paired Evo item is **EV-26-11-05-03.xx** (group-specific remediation; linked
when filed).

## Approach

The change is narrow and opt-in, so existing callers are unaffected.
1. Add a new `workflow_call` input whose default leaves every current caller byte-for-byte unchanged:
   `release-branch` (empty by default), the protected branch name, which must match `release/ios-*`.
2. With it set, preflight still runs from `refs/heads/main` (the control plane) and still checks the
   control commit exactly as today.
3. It additionally verifies a caller-supplied **source** commit:
   - it is on the named branch (the branch tip, or contained in it);
   - the branch's first-parent history from its recorded base A consists only of merge commits of
     merged PRs whose base was that branch;
   - A is contained in `main`;
   - the branch is protected.
4. It outputs the verified source SHA separately from `sha` (the control commit). Callers that do not
   opt in see no output change.

This follows the opt-in pattern of the 2026-11-04 `allow-pinned-source` decision. Design:
`local/handoffs/evo-ui-groups/design-final.md` Appendix J (private).
