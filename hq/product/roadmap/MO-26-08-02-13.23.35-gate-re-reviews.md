## Context

Two of Chris's calls, one change.

**Opus back.** Sonnet ran one review at $0.88 against an Opus average of $1.14 — 23%, not the 80%
the estimate claimed, because it used *more* turns to get there. At that margin the quality question
decides it, and Opus is what found the subtle guard bugs during MO-051's rollout. The gate, not the
model, is what moves the bill.

**Re-reviews should not fire on a push that changed nothing worth re-reading**, with one signal being
whether the push addressed anything the last review raised.

## The gap in the gate that shipped yesterday

MO-26-08-02-03.25.14 asks *does this change contain code?* — right for a first review, wrong for a
second, in both directions:

- It compares against the **merge base**, so a re-review re-reads the whole pull request rather than
  what arrived since anyone looked.
- It skips records-only pushes — including **the push that fixes what the review just asked for**.
  Not hypothetical: the most valuable re-review this rung has done confirmed a fix to a roadmap
  item's prose that it had itself demanded one pass earlier. Under yesterday's gate that confirmation
  would never have run.

## Approach

**Diff against the last reviewed commit, not the merge base.** The previous SHA comes from this
workflow's own run history — the runs already record what was reviewed and when, so nothing new is
stored and there is no cursor that can disagree with reality. A first review finds none and falls
back to the base branch.

**Add the second signal Chris asked for.** The workflow fetches the last review's body and hands it
to the gate. If the incremental change touches a file that review *named*, it is worth re-reviewing —
even when the file is a roadmap item that the code test would skip.

`pathsMentioned` is deliberately a shallow heuristic and errs toward matching. A reviewer writes
paths in prose and any parser for that is guessing; the failure to avoid is guessing *narrowly* and
silently skipping the confirmation pass, so every rule widens rather than narrows. URLs are excluded,
because a review linking to GitHub's docs is not naming a file here and would otherwise make almost
any push look like it addressed something.

**What it does not claim.** It cannot tell whether a finding was actually *fixed* — only that the
push touched the same file. Nothing short of another review can judge the fix, which is the entire
point: this decides whether spending that review is worth it.

## Test plan

- `pathsMentioned`: backticked, bare, parenthesised, with a line number; deduplicated; URLs excluded;
  empty for a review naming no file.
- The gate in both directions — a records-only push that touches a named file is reviewed, one that
  does not is skipped, a code push is reviewed regardless, and an empty prior review does not read as
  naming everything.
- Workflow guards: it diffs against `steps.since.outputs.base`, passes `--prior-review`, and falls
  back to the base branch on a first review.

## Open questions

None. Whether the heuristic is too loose or too tight is answerable only by watching it, and the
reason is printed on every run so the decision is legible in the log.
