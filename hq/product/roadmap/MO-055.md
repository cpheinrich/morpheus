Directed by Chris on 2026-08-01, following MO-054.

**The first thing a new contributor should do on an existing Morpheus project is create their own
`hq/inbox/<github-handle>.md`.** Nothing said so, and nothing made it easy.

`morpheus init` writes an inbox for the project's *initial* owner and never again. A second person
joining an established repo has no inbox, so their agents have nowhere to report and no way to ask
a question — the exchange channel that the whole operating model rests on simply does not exist
for them.

## Why an instruction alone would not have been enough

The inbox format is enforced by `morpheus inbox validate`, which CI runs. A hand-written file gets
the markers, the dense numbering, the summary-before-items rule or the frontmatter wrong, fails
CI, and the contributor's first experience of the project is a red build on a file they were told
to create. That is precisely the friction that makes a step get skipped.

So this ships the instruction *and* the command that satisfies it.

## What changes

- `morpheus inbox init [<handle>]` — writes `hq/inbox/<handle>.md` from the same template `init`
  uses. Defaults the handle to the GitHub login from `gh`, falling back to `git config`
- **Never overwrites**, matching `morpheus init`: running it against an existing inbox reports and
  leaves the file alone, so it is safe for an agent to run speculatively
- `AGENTS.md` — the instruction, in the inbox cycle section
- `architecture.md` — the same, where the inbox is specified

## Where the instruction lives, and why not in the callout

Deliberately **not** added to the MO-054 callout. That block is now byte-identical across six
repos and generated from one exported constant; adding to it means editing five open PRs or
accepting the drift the constant exists to prevent. The callout already sends an arriving agent to
Morpheus's `AGENTS.md`, which is where this now is — so it is reachable by the path MO-054 built.
