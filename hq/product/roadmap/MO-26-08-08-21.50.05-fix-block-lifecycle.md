## Context

Three open issues describe one lifecycle that had split into contradictory behavior. A hand-edited
`status: blocked` without `needs:` is invalid, so the strict parser drops it and `pm block` reports
the existing item as missing. A successful block changes the item but not its generated index,
commits and pushes even from protected trunk, and renders an inbox link as `<id>.md` even though
dated roadmap files carry slugs. Finally, `check pr` tells a blocked branch to move to `review`,
which would claim completion when the branch must retain partial work.

These are not independent polish defects: together they make the safe exit from ambiguous work
misleading, capable of bypassing the repository workflow, and difficult to publish durably.

## Approach

- Recover the precise invalid state `pm block` can repair by validating the raw item again with the
  supplied `needs:`; distinguish an invalid existing item from a missing one.
- Render inbox links from the actual item filename and refresh the roadmap index in the same set of
  explicitly staged files.
- Resolve the configured trunk and refuse normal online blocking there before any write. Preserve
  the offline containment path, which writes locally and never pushes.
- Report the inbox handles that made default owner selection ambiguous.
- Give a blocked claimed branch its own `check pr` guidance: keep the branch and publish records on
  a branch staking no item, never change the status to `review` merely to satisfy a check.

## Acceptance checks

- Blocking a hand-edited, invalid `blocked` item adds `needs:` and leaves the board valid.
- A slugged item produces a resolving inbox link and a refreshed index row reading `blocked`.
- Running online on the configured trunk returns non-zero and changes no item; offline local mode
  remains allowed by the existing gate.
- Two person inboxes produce an error naming both handles.
- A PR from a blocked claimed branch is refused with the records-branch recovery and no instruction
  to claim completion.

## Implementation outcome

- A schema-invalid `blocked` item is recoverable only when the supplied `needs:` makes its complete
  raw frontmatter valid; other invalidity is reported as invalid rather than missing.
- The actual slugged filename flows into the inbox link, and a valid block refreshes and stages the
  generated roadmap alongside the item, worklog and inbox.
- Online blocking refuses the configured trunk before writing. The offline, no-push escape hatch is
  unchanged and its unsent-record report includes the generated index at the caller's actual
  `--dir`, not a restated default path. Ambiguous owner selection names every candidate it found.
- The inbox path is an explicit result field rather than a position in the written-file list, so
  the context receipt re-fingerprints the record this session actually changed.
- Blocked PR guidance preserves the claimed branch and routes publishable records to a non-item
  branch.
- 781 tests pass. TypeScript, the production build, PM validation, generated indexes, and whitespace
  checks are clean.
