MO-054 tells an agent that finds a gap in Morpheus to send it upstream, but said only "an issue or
a pull request". That was left vague because the id scheme made it genuinely unclear.

## What changed

**Timestamp ids (MO-057) removed the reason to keep contributors out of the board.** Under
sequential integers an external agent could not safely create a roadmap item:  allocates
against local files and `origin`, and a contributor's `origin` **is their fork**, so every
contributor would confidently pick the same next number. That risk is gone — a clock needs no
coordination.

With it gone, the argument that was being suppressed wins: **an external agent that hit the
problem can verify the fix.** That is a self-validating change, and the reproduction is the
expensive part to reconstruct from prose.

## Why the contributor must create the item, not the maintainer

`created` and `baseSha` only mean anything if recorded **at the moment the problem was hit**.
`baseSha` is now `HEAD` — the commit the contributor was actually on, which for a fork is
their own version, possibly well behind upstream. A maintainer writing the item afterwards records
the wrong repository state and a date days late, which is the opposite of what the fields are for.

So the item is theirs to write. Morpheus does not assign it one.

## The guidance

- **Open an issue.** It is the durable record, it needs no fork, and it is where triage runs
- **A pull request is welcome**, especially carrying a verified fix
- **Create the roadmap item in that PR** — `morpheus pm new roadmap "..."` records the timestamp
  and `baseSha` correctly
- A PR from outside the project needs a **fork**; issues do not

## Note on fork CI

A `pull_request` from a fork runs with a read-only token and **no secrets**, so
`agent-review` — which needs `ANTHROPIC_API_KEY` — skips. First-time contributors also need
manual approval before any workflow runs. Worth stating so a contributor is not surprised, and
worth remembering before relying on that rung for external work.
