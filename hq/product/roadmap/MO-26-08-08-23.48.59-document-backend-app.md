## Context

The canonical project tree names client surfaces under `apps/` and narrowly defines
`packages/shared/` as code consumed by multiple surfaces. A deployed product without a client UI
therefore has no documented home. Lakina exposed the gap with its Python trading engine: putting it
under `packages/shared/` would erase that directory's contract, while a local `apps/trader/` name
would not generalise.

## Approach

Add optional `apps/backend/` to the canonical tree and business-function table. Define it as the
home for deployable workers, services, scheduled jobs, inference systems, and execution loops, and
state the boundary with `packages/shared/`: runnable product code goes in `apps/backend/`; code
imported by multiple surfaces goes in `packages/shared/`.

## Acceptance

- The canonical tree names `apps/backend/` as an optional deployable surface.
- The business-function table identifies the same location and representative workloads.
- The prose makes the `apps/backend/` versus `packages/shared/` boundary unambiguous.
- The project manifest can declare whether the backend surface exists.
- A non-TypeScript backend has an explicit relationship to shared TypeScript schema sources.
- The change does not require every project to scaffold an unused backend directory.
