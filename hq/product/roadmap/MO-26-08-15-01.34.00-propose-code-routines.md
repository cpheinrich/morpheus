## Context

Everything the operating model does improves the codebase one item at a time, and nothing looks at
the whole of it. Duplication accumulates between modules no single item touches, dead code survives
because deleting it is nobody's task, and a flaky test is tolerated by every session busy doing
something else. A board whose unit is the feature cannot see any of it.

Chris raised this after
[Boris Cherny's account](https://x.com/bcherny) of running ~12 daily maintenance routines across
Claude Code's repositories — crash fuzzer, dup unifier, dead-code remover, abstraction police,
flaky-test fixer and more. Reported result: **388 pull requests over a few weeks, 180 merged.**

That number is the design input. A 46% merge rate is good for a machine that costs nothing to run,
and it also means **208 pull requests a human opened and rejected**. Anthropic absorbs that; a
one-operator company does not. Chris's review time is the bottleneck the inbox format was already
redesigned around, and a routine fleet at that hit rate would consume it while feeling productive.

## Approach

**This item is the proposal only** — `architecture.md` §7.11, marked as not built. No routine, no
workflow, no CLI surface ships here, because the decisions in §7.11.8 change the shape of all
three.

The design is organised around earning the right to open a pull request rather than generating more
of them:

- **Routines never enter the feature lane.** Separate surface, separate budget: a routine flood
  cannot starve the board and a full board cannot silence maintenance. This is what keeps §7.8's
  *dispatcher, not a doer* intact — routines would otherwise reverse it by the back door, and
  reverse it harder, since a routine does not pick work, it writes it.
- **A deterministic scan runs before any model**, so a routine that finds nothing costs nothing —
  the same property that made an hourly heartbeat affordable.
- **One pull request per routine per run**, not one per finding. It asks the reviewer *is this class
  of change correct here* once rather than twelve times, and it stops per-finding review costs
  multiplying a bill this repo has already learned is moved by the gate rather than the model.
- **Merge rate is a control loop**, with automatic, reported suspension below a floor. Without it
  every routine stays as good as the day it was written.
- **Three stages, and stage 0 opens nothing** — report first, on Morpheus only, until a week of
  findings has been read. Directly modelled on two recorded decisions: *the review rung proves
  itself on one repo first*, and *dispatch stays refusing until the beats have been read*.
- **Not every finding is a pull request.** Mechanical ones are; judgment calls become roadmap items
  and open questions become inbox items. That is what stops "improve the abstractions" becoming a
  machine for confidently wrong refactors.
- **Reuse falls out of §18** — catalogue and prompts versioned in Morpheus, a `code-health.yml`
  reusable workflow referenced `@main`, selection and budgets in the CLI where there is a type
  checker, enablement per project in `morpheus.json`, and the cron in the calling repo.

§7.11.7 names the routines only Morpheus could run — convention drift against the scaffold,
deviation drift against the manifest, record drift against `.agent/decisions.md`. Evo was three
scaffold generations behind and carried an undeclared `output: "export"` deviation for months;
both surfaced as blocked work rather than as a diff. Those are the reason to build machinery
rather than one-off scripts.

Implementation is deliberately not scoped here. It becomes separate items once §7.11.8 is answered.
