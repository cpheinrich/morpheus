## Context

`pm-check.yml` already checks out and builds Morpheus to validate project records and generated
indexes. A downstream project with generated Firestore role helpers currently repeats that entire
setup in a separate job just to run one more CLI command. The duplicated setup includes details such
as `package_json_file: .morpheus/package.json` whose failure mode only appears in consumers.

The rule check is security-relevant: it proves the claim writer, route gate and Firestore data gate
still share one role vocabulary. It belongs beside the other generated-state checks, but projects
without Firestore rules must not start failing merely because reusable workflows pin `@main`.

## Approach

- Add a string `hq-rules-path` workflow-call input, defaulting to empty. The path is the opt-in value
  so the check names the rules file Firebase actually deploys.
- When set, pass that path to `hq rules --check --rules-path` after the build already used by the PM
  validations.
- Parse the workflow in tests and pin the input's type/default, the conditional, and the exact
  command so a comment or disconnected input cannot make the test pass.
- Document the one-line consumer configuration beside the three-reader access invariant.

## Acceptance checks

- A caller omitting `hq-rules-path` preserves current behavior.
- A caller setting `hq-rules-path: infra/firebase/firestore.rules` runs the check against that
  deployed file and refuses missing, unmarked, or stale helpers.
- The workflow remains valid YAML and the complete test/type/build/PM suite passes.

## Implementation outcome

- `pm-check.yml` declares `hq-rules-path` as an empty-by-default string and conditionally runs the
  existing CLI against that explicit path after the job's one checkout/build sequence.
- The CLI accepts the same `--rules-path`, reports it in every remedy, and refuses to invent missing
  parent directories that could turn a typo into a second, undeployed security file.
- `morpheus init` writes the deny-by-default starter to the company layout's canonical
  `infra/firebase/firestore.rules`, while preserving and reporting an established root gate instead
  of creating a duplicate. Fresh-project CI is wired to the canonical path in the same operation;
  migrated root-layout repos stay unwired until their deployed path is confirmed. The CLI requires
  a non-empty path and has no root fallback.
- The workflow test parses the executable structure and pins the input type/default, conditional,
  and command. This matches GitHub's documented typed reusable-workflow input model.
- The architecture shows the one-line downstream configuration and explains why absence is not an
  error for projects without a Firestore data gate.
- 787 tests pass. TypeScript, the production build, PM validation, generated indexes, and whitespace
  checks are clean.
