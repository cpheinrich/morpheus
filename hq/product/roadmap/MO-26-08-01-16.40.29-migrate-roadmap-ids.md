## Context

MO-057 shipped the dated id scheme and the `pm migrate-ids` command but left the board on integers,
so the mechanism could be reviewed before it touched anything. This runs it against Morpheus.

56 items move from `MO-001` to `MO-26-07-28-001` — the item's **own** creation date plus its old
number. One item created after MO-057 landed is already dated and is left alone.

## Why the old number stays in the id

Git history, commit messages and merged pull requests say `MO-045` and cannot be rewritten.
Keeping the number as the last field means `grep MO-045` still finds the item. A body note records
the rename where a reader lands.

## What else moved

**32 worklog entries carry `roadmap: MO-052` in frontmatter.** That is a structured reference, not
prose — a tool resolving it would find nothing after the rename, so the migration repoints them.
Prose mentions are deliberately untouched: the number is still in the new id, and rewriting
narrative in a historical record would be editing the past rather than repairing a link.

## Test plan

Captured every item's title, status, priority, `prs`, `created`, `goal` and a hash of its body
before migrating, then compared after:

| Check | Result |
|---|---|
| Item count | 57 → 57 |
| Items lost | 0 |
| Field drift across all seven fields | 0 |
| Ordering (old sequence vs new lexicographic) | **unchanged**, 56 items compared |
| Dangling `roadmap:` references | 0 |

Body hashes are compared with the inserted migration note stripped, so the comparison is
like for like. `migrate` refuses outright rather than warning if the rewrite would reorder the
board, and `pm validate`, `pm index --check` and the full suite pass.
