## Context

Commit `790ae1ff` (2026-10-06) removed the conventions job's concurrency group so a cancelled run
could no longer block a merge. Superseded runs have run to completion since then and failed on the
reusable `pr-check.yml` live-head check, `jq -e '.head.sha == $sha'`, with no message at all. Those
red runs sit on commits nobody can merge, and agents and people chase them. Evo calls
`pr-check.yml@main`, so the same noise appears there: about 31% of Evo's conventions failures after
10-08 in the sample reported to Chris.

## Approach

When the live pull request has moved to a newer head, print
`::notice::superseded by <sha>; this run's result is moot`, add a line to the step summary, and
exit 0 without running the checks. Do not reintroduce `cancel-in-progress`.

A pass cannot count for the newer head, because GitHub attaches a `pull_request` run's check to the
SHA its event named, and branch protection reads the current head's own check runs. That argument
needs the PR to have actually moved after the event. A read that lags the event can show the
previous head while the event's head is still current, so the guard passes only when GitHub's copy
is strictly newer than the payload (`updated_at`). An older or equal copy, or a value that is not a
SHA or a timestamp, fails closed with its reason.

Tests run the step's own script with `gh` and `node` stubbed. They cover a superseded head (notice,
exit 0, `check pr` never invoked), the current head (the checks run), the equal-timestamp boundary,
and missing or malformed values.
