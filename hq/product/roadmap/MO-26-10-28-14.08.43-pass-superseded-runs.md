## Context

Commit `790ae1ff` (2026-10-06) removed the conventions job's concurrency group so a cancelled run
could no longer block a merge. Superseded runs have run to completion since then and failed on the
reusable `pr-check.yml` live-head check, `jq -e '.head.sha == $sha'`, with no message at all. Those
red runs sit on commits nobody can merge, and agents and people chase them. Evo calls
`pr-check.yml@main`, so the same noise appears there: about 31% of Evo's conventions failures after
10-08 in the sample reported to Chris.

## Approach

When the live pull request has moved to a newer head, print
`::notice::superseded by <sha>; this run's result is moot`, add a line to the step summary, and
pass without running the checks. Do not reintroduce `cancel-in-progress`.

The pass must never count as the required `pr / conventions`. GitHub attaches a `pull_request`
run's checks to the SHA its event named, so the pass does not land on the newer head. But the PR can
be force-pushed back to that SHA, so a pass under the required name would fail open there. A new
`head` job therefore decides first, and the required job takes its name from that decision:
`superseded` when the PR provably moved, `conventions` otherwise.

The decision needs proof of a move. A read that lags the event can show the previous head while
the event's head is still current, so supersession requires GitHub's copy to be strictly newer than
the payload (`updated_at`). An older or equal copy, a malformed value, a failed or cancelled `head`,
and a move after `head` decided all fail `pr / conventions` with their reason.

Tests run the steps' own scripts with `gh` and `node` stubbed, and check the job topology and the
evaluated name expression.
