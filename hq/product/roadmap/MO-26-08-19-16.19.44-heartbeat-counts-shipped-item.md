## Context

A downstream project's board stopped dispatching work for a week. `morpheus heartbeat` reported
**8 items in flight against a ceiling of 3** and picked nothing, on the reasoning that finishing
beats starting. The true number in flight was three.

Five of the eight were branches whose pull requests had merged days earlier and which still existed
on `origin`. `listClaims` reads every `refs/remotes/origin/*` matching an item id, which is correct
— that ref is exactly what makes `pm claim` refuse a taken item. But `assess` then counted those
refs toward the dispatch ceiling, and a branch behind a shipped item is not work in progress.

The refs survive because a squash-merge only deletes the branch when the merger passes
`--delete-branch` or the repository sets `delete_branch_on_merge`. The project's own convention
includes the flag, so agents following it leave nothing behind; a merge from the GitHub UI does.
That is a repository setting rather than a Morpheus defect — but Morpheus is where the consequence
lands, and it lands as paralysis rather than as an error.

**Why it went unnoticed for a week.** `pm claims` listing stale entries reads as untidiness, and the
remedy — five `git push origin --delete` lines — was printed by `pm ship` every run. Nobody
connected that to the board declining to hand out work, because the beat's explanation for
dispatching nothing is indistinguishable from the healthy case where three real items are underway.

## Approach

`assess` already excludes `blocked` from the in-flight count, with the reasoning that a claim
waiting on a person holds no lane. `shipped` and `dropped` are the same argument one step further
on: the work is over.

Extend that exclusion rather than adding a new mechanism. `claimedIds` keeps counting all three, so
drift and candidate ranking still respect the surviving ref — `pm claim` really is blocked by it,
and the beat should keep saying so. Only the ceiling changes.

## Acceptance checks

- A claim whose item is `shipped` or `dropped` does not occupy a dispatch lane.
- A genuinely in-progress claim beside a shipped one is still counted.
- `blocked` behaviour and the drift and candidate lists are unchanged.

## Outcome

`SETTLED_FOR_DISPATCH` in `src/heartbeat/assess.ts` now holds `blocked`, `shipped` and `dropped`,
and `inFlight` filters on it. The `blockedIds` binding it replaced was removed rather than left
unused.

Two tests in `tests/heartbeat.test.ts`, both mutation-checked: narrowing the set back to `blocked`
alone fails exactly those two and no others (939 passing, 2 failing). 941 pass with the fix;
typecheck clean.

**Not addressed here, deliberately.** Whether Morpheus should surface the underlying repository
setting — `delete_branch_on_merge: false` is what generates these refs in the first place, and
`doctor` is the plausible home for noticing it — is a separate question and a separate item if
wanted. This change makes the symptom harmless; it does not stop the refs accumulating.
