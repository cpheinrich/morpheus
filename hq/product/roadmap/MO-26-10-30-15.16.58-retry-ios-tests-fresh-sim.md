## Context

Evo's CD calls `ios-ci.yml` with `test-iterations: 3` on a self-hosted tart VM. Those retries ran
inside the same simulator and xcodebuild session (`-retry-tests-on-failure`), so a UI test that
failed because of state an earlier test left in the simulator or the app's container failed all
three iterations. Of six test-job failures in Evo delivery runs since 2026-10-20, four were UI
tests failing every iteration (for example run 40607407673). Chris's direction (2026-10-30): checks
that protect users block, everything else warns; simplify instead of adding machinery; production
differs from staging only by running more automated tests.

## Approach

- Attempt 1 runs the caller's selection unchanged. On failure, `scripts/ios-test-retry.py` erases
  the job-owned simulator, reruns the caller's pre-test script, and starts a new xcodebuild with
  `-only-testing` of the failed identifiers and `-collect-test-diagnostics never` where supported.
  `test-iterations` keeps its name and becomes the total attempts, default 3.
- A test that fails and then passes on a clean retry is flaky: a warning annotation, a job-summary
  line and a `flaky-tests` JSON workflow output, never a job failure. A test that fails every
  attempt fails the job. A failure that names no test is never retried away.
- Scope stays with the caller through the existing `test-plan`, `only-testing` and `skip-testing`
  inputs, now documented as the staging-smoke and production-full lever.
- Evo's adoption (pins, `actions-ref`, its result validator reading `test-attempts.json`) is a
  separate stage.

## Acceptance

- Script-level tests fail if retries stop erasing the simulator or if a pass on a clean retry
  fails the job.
- A real xcodebuild run shows a leftover-state test failing attempt 1 and passing its clean retry.
