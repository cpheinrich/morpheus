## Context

When a test bundle cannot start (the test runner or host app fails to install or launch on the
simulator), Xcode records no real test results for that bundle. Instead the xcresult contains a
placeholder `Test Case` under a `System Failures` suite, named like "<App> encountered an error",
with a failure such as "Failed to install or launch the test runner".

`scripts/ios-test-retry.py` read that placeholder as an ordinary test id and retried
`-only-testing:<Bundle>/<App> encountered an error`. Xcode selected nothing, ran zero tests in
that bundle and exited 0, so the bundle's real tests were never rerun, the placeholder stayed
"failing" on every attempt, and the job failed with a fictional test id while every unit result
was absent. Observed on a consumer's staging delivery (November 2026); UI tests in the same run
recovered after the simulator erase, so the defect is the retry classification, not hardware.

## Approach

Recognise a bundle-level failure from the xcresult structure (a `Test Case` that is not a
selectable `Class/method()` test) and retry the failed bundle's original selection on the erased
simulator: the caller's `-only-testing` entries inside that bundle (or the whole bundle when the
caller selected all of it), with the caller's `-skip-testing` carried through. Never widen past the
caller's selection, never rerun unrelated passing tests, and never count a retry that executed
none of the bundle's tests as recovery. Attempt counts, caller policy, evidence shape and the
fail-closed handling of unattributable failures are unchanged.
