## Context

Reported by Chris in [#60](https://github.com/cpheinrich/morpheus/issues/60), found doing ordinary
work in `cpheinrich.com`. Two items were filed; **one was already fixed** by #62, which made the
generated index link to the item's real filename instead of reconstructing `./<id>.md`. That leaves
one, and it is worse than the report describes.

`listClaims` carried a private copy of the roadmap-id pattern that MO-057 left behind:

```ts
const m = /^([a-z]{2,4}-\d{3,})-/i.exec(branch);
```

The issue reports the truncation it produces — `cph-2026-08-01-22.49.21-…` reading as `CPH-2026`,
an id no item could have. But against the form `pm new` produces **today**, after the
four-digit-year normalisation in #63, it does not match at all:

| Branch | Old parser |
|---|---|
| `cph-2026-08-01-22.49.21-keep-hq-brand` | `CPH-2026` — truncated |
| `mo-26-08-01-17.28.41-voice-handoff` | **no match** |
| `mo-26-07-29-045-something` | **no match** |
| `mo-045-legacy` | `MO-045` |

**A branch that fails to parse is not reported — it is dropped.** Every caller reads absence as
"nothing claims this", so `listClaims` returned a short list, or an empty one, from a remote full of
claims.

### What that reached

`listClaims` has two consumers, and the second is where it matters.

`pm claims` showed the wrong table, which is what Chris saw. **The heartbeat computes its entire
view of what is in flight from the same list**, so all three of MO-050's guards degraded silently:
the ceiling counted fewer items than existed, a blocked item could not be matched to its claim so it
stopped being excluded from the count, and a claimed item read as unclaimed and was offered as the
next thing to pick.

Enforcement was never affected: `pm claim` refuses via `findClaims`, which queries `ls-remote` with
an explicit branch prefix and never had this pattern. So the failure was confined to *reporting* —
nothing was double-claimed. That is luck rather than design, and the report understating it is
exactly what a silent parser buys.

## Approach

The issue proposes the fix and it is the right one: one parser, and stop keeping a second copy.

`roadmapIdFromBranch` moves from `src/check/pr.ts` to `src/pm/id.ts`, beside the patterns it has to
agree with, and `check/pr.ts` re-exports it so nothing importing it has to change. `listClaims`
calls it instead of its own regex.

The parsing also comes out of the git call as `parseClaimRefs`, for the reason `parseClaimedNumbers`
already did in the same file: parsing is where this goes wrong, and it cannot be tested while it is
welded to a subprocess. That absence is why the drift went unnoticed — the whole suite passed
against a parser that returned nothing.

Also: `pm claims` sized its columns for `MO-045`, so a twenty-character id destroyed the alignment.
Widths now come from the data.

## Test plan

- `parseClaimRefs` across all four branch shapes, including the exact branch from the issue.
- A drift guard asserting `parseClaimRefs` and `roadmapIdFromBranch` agree on every shape — two
  parsers agreeing is precisely what stopped being true.
- The heartbeat's three guards re-exercised with **timestamp ids parsed from real branches**. Every
  existing heartbeat test used `MO-001`, which is why they all passed while the claim list was
  empty.
- Verified by reverting the parser and confirming **10 tests fail**, including the ceiling guard.
- End to end against the real remote: `pm claims` and `heartbeat` both round-trip the full id.
