## Context

Chris thinks well out loud. Voice mode is good for that and has none of a working session's
capabilities — it cannot read the repository, run the CLI, or see the board, and it starts cold
every time. Today the only bridge is him re-explaining Morpheus from memory, and the way back is
pasting a transcript and hoping.

This has already produced value once: the heartbeat and verifier stack (MO-048 through MO-052) began
as a voice conversation. The single most useful line in that handoff was the one telling the next
agent it could not see the codebase and should defer to it — which is what caused a prompt-based
heartbeat design to be checked and killed rather than built. That line was written by hand. It
should not depend on remembering to.

## Approach

**One split, and it is the whole design.** What the project *is* changes when a convention does;
what the board looks like *today* is stale in hours. The first goes into claude.ai project knowledge
once; the second is regenerated per session and pasted.

| Command | Writes | Lifecycle |
|---|---|---|
| `morpheus voice knowledge` | `local/voice/knowledge.md` | uploaded once, refreshed on a convention change |
| `morpheus voice brief "<topic>"` | `local/handoffs/YYYY-MM-DD-<slug>.md` | every session |

Verified in the UI rather than inferred: **voice mode is available inside a project chat** — the
composer offers it whenever the Chat/Cowork toggle is on Chat. The help doc's caveat is about
running voice *as Cowork*. What could not be verified is whether project knowledge actually reaches
the voice conversation, so `--full` inlines the explainer and the workflow is correct either way.

**The two directions are asymmetric.** Out is deterministic — board, inbox, commits since the last
handoff — so it is a CLI command, testable and free to every scaffolded project. Back is judgment:
a returning spec was written without the codebase in view, so ingesting it means checking it against
the repository and finding the false premises. That is `.claude/skills/voice-import`, and no
deterministic command could do it.

`local/handoffs/` is canonical for both directions and never committed. Handoffs are correspondence;
what is worth keeping becomes an item, a decision, or a worklog entry, and those are committed.

## Test plan

- Pure builders under test: the explainer carries the defer-to-the-codebase caveat, refuses to draft
  roadmap items, permits reaching no conclusion, and uses the *calling project's* prefix.
- The brief leads with the topic, states what blocked work needs rather than counting it, names open
  inbox items, and distinguishes an unreadable git history from an empty one.
- `latestHandoffDate` returns null rather than a default window when there is no previous handoff.
- `isoDateInZone` is still the Pacific day at 17:30 Pacific, when UTC has already rolled over.
- The shipped skills are asserted to keep the instructions that were learned the hard way.
- Run end to end against the real repo, which is what found both bugs.

## Open questions

None. Whether the skills should be scaffolded into other projects is deliberately deferred — the
capability already reaches them through the CLI, and there is one use so far.
