## Context

Raised by the agent review rung itself, on
[#69](https://github.com/cpheinrich/morpheus/pull/69) — the pull request that fixed it being unable
to post. Also tracked as [issue #70](https://github.com/cpheinrich/morpheus/issues/70).

#69 fixed the *cause* of #68's silent failure and wrote the lesson into `.agent/learned.md`:

> Ask what the check looks like when the reporting path is broken — if the answer is "the same as
> success", the check is not finished.

**After that change, the answer is still "the same as success."** Nothing distinguishes *reviewed
and posted* from *reviewed and denied*. Plausible next causes, none hypothetical:

- `--max-turns 40` exhausted mid-post
- a tool name changing in a future version of the action
- `classify_inline_comments` (default `true`) buffering findings the post-step then drops
- a comment API failure

Each reproduces #68 exactly, and the only detector is a human noticing four minutes of runtime with
nothing to show — the detector that cost a full live run to fire the first time.

## Approach

**Key on delivery, not on denials — and "delivery" means a comment that carries a review**, not a
comment that exists.

The obvious definition is a trap, verified in the action's source. With `track_progress: true` a
comment is *created before the model has seen the diff* (`createInitialComment`, called ahead of
`fetchGitHubData` in `src/modes/tag/index.ts`) and *updated in a `finally` that always runs*
(`updateCommentLink` in `src/entrypoints/run.ts`), rewriting the body to
`**Claude encountered an error after Xm Ys**` when the run died. Created ✓, updated ✓, review
delivered ✗ — so a created-or-updated trigger can never fire.

The trigger inspects the **final body** for one exact string:

```
I'll analyze this and get back to you.
```

from `createCommentBody` (`src/github/operations/comments/common.ts:30`). Present ⟺ the reviewer
never wrote anything — `mcp__github_comment__update_claude_comment` *replaces* the body rather than
appending (`src/mcp/github-comment-server.ts`), so the sentence is gone the moment a real review
lands. That biconditional is what the three earlier definitions all lacked.

**Do not probe for `Claude Code is working…`**, the visible, canonical-looking half of the same
placeholder. `updateCommentBody` strips exactly that line and nothing else
(`workingPattern` at `comment-logic.ts:84–85`) on *every* run, success or failure, then re-emits the
remainder. A probe for it fires never. The two lines are written together and only one survives.

Combine with the run's own success signal from `execution_file` for diagnosis once the alarm fires.

That distinction is the whole item, so it is worth showing why. Of the four causes above:

| Cause | Produces a denial? | Caught by a delivery check? |
|---|---|---|
| turn cap exhausted mid-post | no | **yes** |
| a tool renamed upstream | yes | **yes** |
| `classify_inline_comments` dropping buffered findings | **no** — the call succeeded, the post-step discarded it | **yes** |
| comment API failure | **no** — a tool *error*, a different field | **yes** |

And in the other direction: **denials are routinely non-zero on a healthy run.** Compound `Bash`
commands are not in tag mode's allowlist, so a review that posts perfectly well still accumulates
several. A `denials > 0` trigger would fire on runs that worked, get muted within a week, and leave
us back at #68 with an extra step — which is exactly what `.agent/decisions.md` warns about under
*a model-graded reviewer that gets ignored is worse than none, because the rung then reads as
covered.*

The mechanism: give the Review step an `id:` — it has none today, so `execution_file`
(`action.yml:170`) is unreachable — and add an `if: always()` step that fetches the tracking
comment's final body and flags the placeholder and error forms, emitting a warning annotation and a
job-summary line. Mirror the shape of
the existing "Report the rung as unconfigured" step: the two failures should look the same to a
reader, because to a reader they are the same failure.

`execution_file` stays useful for *diagnosis* once the alarm fires. It is just not the trigger.

## Resolution

The workflow now snapshots this run id's tracking comment before the action, gives the Review step
an id, and inspects the final tracking comment from a separate dependent job — after the composite
action's post step has finalized it. A typed predicate requires a new comment id, the pinned
action's positive finished marker, the Morpheus-owned sanitizer-safe Markdown reference sentinel
appended by the CLI to every assembled prompt, and substantive review text that is neither the
exact initial placeholder nor the action's error form. A progress body that merely mentions the
sentinel is still rejected when it carries the pinned-action spinner image anywhere in the review
body or an unticked checklist
outside quoted code. The comment is selected by its own `[View job]` run
URL across every API page rather than by generic bot recency. The workflow emits
the same warning-and-summary shape as the unconfigured rung when any evidence is absent; it remains
advisory, consistent with the verifier-stack decision.

Issue #76's three related gate defects are fixed in the same boundary:

- GitHub blob permalinks and decoded `claude.ai/code?q=...` Fix-this links contribute their
  repo-relative paths before other URL text is removed.
- The workflow and its structural test pin `steps.since.outputs.base` to the cost gate; the Review
  action receives the full-PR prompt and no incremental base.
- `needed(null)` is the unreadable-diff fail-open state, while a real `needed([])` now skips because
  nothing changed since the last review.

The first live run exposed two facts the original item did not account for: the current model
replaces the action's initial sentence with a `### Reviewing this PR` checklist before it reports,
and a normal step after a composite action still runs *before* that action's post step. The first
would have made "placeholder absent" a false success; the second meant the supposed final body was
not final. The positive finished marker, progress-form rejection, immutable action pin and separate
delivery job are the corrections. A second live run then proved that negative strings cannot be
searched across reviewer prose — a healthy review of this detector quoted both — and that progress
headings are model-authored and unstable. Negative checks are now scoped to the action header or
whole placeholder section, while the positive sentinel is controlled by this repository and ships
in the assembled prompt with the detector rather than relying on a consumer's copied persona.

## Why this is filed rather than folded into #69

On the reviewer's own recommendation: #69's item was "the reviewer could not post its review", and it
did. But this belongs in the board rather than as a paragraph in `learned.md`, because **a lesson
recorded and not instrumented is how this recurred in the first place** — which is the argument
`learned.md` itself makes.

## Test plan

- A guard in `tests/workflows.test.ts` asserting the Review step has an `id` and that a follow-up
  step runs `if: always()` — without the `id` the output is silently unavailable, which is the same
  class of failure again.
- **Exercise the delivery axis, not the denial axis.** Forcing a denial would pass while the
  buffering and API-failure cases stayed invisible, and would also fire on healthy runs. The honest
  test is to suppress *delivery* — revoke the comment tools on a scratch branch — and confirm the
  run is flagged rather than green.
- A negative test that matters as much: a healthy run with non-zero denials must **not** be flagged.
- And the one that catches the trap above: a run whose comment exists but still holds the
  placeholder body **must** be flagged. Any detector that passes this while failing that is testing
  the comment's existence, not the review's.

## Open questions

Whether a denied review should **fail** the check rather than warn. Rung 2 is advisory by design and
a model-graded gate that fails on its own noise gets bypassed — but "the reviewer was silenced" is a
different fact from "the reviewer had nothing to say", and arguably the first is infrastructure
rather than judgment. Left for whoever claims this.

**Resolved:** warn. Delivery failure is called out as infrastructure evidence rather than a clean
review, but it does not turn the independent model's advisory rung into a merge gate. A separate
automated check or human can still act on the warning without teaching contributors to bypass rung
2 whenever the model or its action is noisy.

## How this item was specified wrong, first time

Filed with a `denials > 0` trigger — the shape the reviewer proposed on its first pass and
**retracted on its second**, in a "Smaller" note giving the evidence above. I missed the retraction
because I read the second review partially and stopped before that section, then wrote the item from
the superseded recommendation. The third pass caught it.

Worth recording because the failure is not "the reviewer was wrong": it corrected itself
unprompted, one pass later. Reading a review partially is how a withdrawn recommendation gets
implemented, and it is a cheaper mistake to make than to find.

## The pattern worth naming

Five review passes, five corrections, and **not one of them was about the diagnosis** — which was
right from the first sentence: nothing distinguishes a review that landed from one that did not.
Every correction was to the *operational definition of "it worked"*:

1. denials non-zero → misses two causes, and fires on healthy runs
2. comment created or updated → always true, so it can never fire
4. body still holds `Claude Code is working…` → stripped on every run, so it can never fire either
5. body still holds `I'll analyze this and get back to you.` → what the item now says

Each definition was plausible, and each would have shipped a detector that reported success in the
state it existed to catch. That is the same failure as #68 one level up, three times in a row, which
suggests it is not carelessness but the actual difficulty: **for anything whose job is to report,
defining "it reported" is harder than building the check, and a wrong definition is invisible
precisely because it always passes.**

Twice the reviewer retracted its own recommendation from the previous pass. That is the argument for
rung 2 in one line: not that it is right, but that it is independent enough to catch itself.
