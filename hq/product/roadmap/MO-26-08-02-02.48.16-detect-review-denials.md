## Context

Raised by the agent review rung itself, on
[#69](https://github.com/cpheinrich/morpheus/pull/69) — the pull request that fixed it being unable
to post. Also tracked as [issue #70](https://github.com/cpheinrich/morpheus/issues/70).

#69 fixed the *cause* of #68's silent failure and wrote the lesson into `.agent/learned.md`:

> Ask what the check looks like when the reporting path is broken — if the answer is "the same as
> success", the check is not finished.

**After that change, the answer is still "the same as success."** Nothing distinguishes *reviewed
and posted* from *reviewed and denied*. Plausible next causes, none hypothetical:

- `--max-turns 40` exhausted mid-post
- a tool name changing in a future version of the action
- `classify_inline_comments` (default `true`) buffering findings the post-step then drops
- a comment API failure

Each reproduces #68 exactly, and the only detector is a human noticing four minutes of runtime with
nothing to show — the detector that cost a full live run to fire the first time.

## Approach

The action exposes `execution_file` (`action.yml:170`) — the JSON that already carried
`permission_denials_count: 9` on the failing run. **The Review step has no `id:`, so that output is
currently unreachable.**

Give it one, then add an `if: always()` step that reads the file and emits a warning annotation plus
a job-summary line when denials are non-zero or the run hit the turn cap. Mirror the shape of the
existing "Report the rung as unconfigured" step — that is the part of this workflow that already
gets this right, and the two failures deserve to look the same to a reader.

## Why this is filed rather than folded into #69

On the reviewer's own recommendation: #69's item was "the reviewer could not post its review", and it
did. But this belongs in the board rather than as a paragraph in `learned.md`, because **a lesson
recorded and not instrumented is how this recurred in the first place** — which is the argument
`learned.md` itself makes.

## Test plan

- A guard in `tests/workflows.test.ts` asserting the Review step has an `id` and that a follow-up
  step reads `execution_file` — without the `id` the output is silently unavailable, which is the
  same class of failure again.
- Exercise by forcing a denial: temporarily narrow `--allowedTools` on a scratch branch and confirm
  the run goes red-flagged rather than green.

## Open questions

Whether a denied review should **fail** the check rather than warn. Rung 2 is advisory by design and
a model-graded gate that fails on its own noise gets bypassed — but "the reviewer was silenced" is a
different fact from "the reviewer had nothing to say", and arguably the first is infrastructure
rather than judgment. Left for whoever claims this.
