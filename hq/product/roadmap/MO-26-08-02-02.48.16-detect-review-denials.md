## Context

Raised by the agent review rung itself, on
[#69](https://github.com/cpheinrich/morpheus/pull/69) — the pull request that fixed it being unable
to post. Also tracked as [issue #70](https://github.com/cpheinrich/morpheus/issues/70).

#69 fixed the *cause* of #68's silent failure and wrote the lesson into `.agent/learned.md`:

> Ask what the check looks like when the reporting path is broken — if the answer is "the same as
> success", the check is not finished.

**After that change, the answer is still "the same as success."** Nothing distinguishes *reviewed
and posted* from *reviewed and denied*. Plausible next causes, none hypothetical:

- `--max-turns 40` exhausted mid-post
- a tool name changing in a future version of the action
- `classify_inline_comments` (default `true`) buffering findings the post-step then drops
- a comment API failure

Each reproduces #68 exactly, and the only detector is a human noticing four minutes of runtime with
nothing to show — the detector that cost a full live run to fire the first time.

## Approach

**Key on delivery, not on denials.** The trigger is: did a comment get created or updated by this
run? Everything else is a proxy that misses cases or fires on healthy ones.

That distinction is the whole item, so it is worth showing why. Of the four causes above:

| Cause | Produces a denial? | Caught by a delivery check? |
|---|---|---|
| turn cap exhausted mid-post | no | **yes** |
| a tool renamed upstream | yes | **yes** |
| `classify_inline_comments` dropping buffered findings | **no** — the call succeeded, the post-step discarded it | **yes** |
| comment API failure | **no** — a tool *error*, a different field | **yes** |

And in the other direction: **denials are routinely non-zero on a healthy run.** Compound `Bash`
commands are not in tag mode's allowlist, so a review that posts perfectly well still accumulates
several. A `denials > 0` trigger would fire on runs that worked, get muted within a week, and leave
us back at #68 with an extra step — which is exactly what `.agent/decisions.md` warns about under
*a model-graded reviewer that gets ignored is worse than none, because the rung then reads as
covered.*

The mechanism: give the Review step an `id:` — it has none today, so `execution_file`
(`action.yml:170`) is unreachable — and add an `if: always()` step that checks whether a comment
landed, emitting a warning annotation and a job-summary line when one did not. Mirror the shape of
the existing "Report the rung as unconfigured" step: the two failures should look the same to a
reader, because to a reader they are the same failure.

`execution_file` stays useful for *diagnosis* once the alarm fires. It is just not the trigger.

## Why this is filed rather than folded into #69

On the reviewer's own recommendation: #69's item was "the reviewer could not post its review", and it
did. But this belongs in the board rather than as a paragraph in `learned.md`, because **a lesson
recorded and not instrumented is how this recurred in the first place** — which is the argument
`learned.md` itself makes.

## Test plan

- A guard in `tests/workflows.test.ts` asserting the Review step has an `id` and that a follow-up
  step runs `if: always()` — without the `id` the output is silently unavailable, which is the same
  class of failure again.
- **Exercise the delivery axis, not the denial axis.** Forcing a denial would pass while the
  buffering and API-failure cases stayed invisible, and would also fire on healthy runs. The honest
  test is to suppress *delivery* — revoke the comment tools on a scratch branch — and confirm the
  run is flagged rather than green.
- A negative test that matters as much: a healthy run with non-zero denials must **not** be flagged.

## Open questions

Whether a denied review should **fail** the check rather than warn. Rung 2 is advisory by design and
a model-graded gate that fails on its own noise gets bypassed — but "the reviewer was silenced" is a
different fact from "the reviewer had nothing to say", and arguably the first is infrastructure
rather than judgment. Left for whoever claims this.

## How this item was specified wrong, first time

Filed with a `denials > 0` trigger — the shape the reviewer proposed on its first pass and
**retracted on its second**, in a "Smaller" note giving the evidence above. I missed the retraction
because I read the second review partially and stopped before that section, then wrote the item from
the superseded recommendation. The third pass caught it.

Worth recording because the failure is not "the reviewer was wrong": it corrected itself
unprompted, one pass later. Reading a review partially is how a withdrawn recommendation gets
implemented, and it is a cheaper mistake to make than to find.
