## Context

The operator authorized Darwin and Evo Factory execution identities to use their declared private Darwin credentials companion for relevant task context. Related-workspace checkouts already support enrolled, revision-pinned, protected credential companions; ordinary single-project Fleet checkouts do not attach them. A live QA worker therefore could not retrieve service definitions needed for its task.

## Approach

Reuse the existing companion pointer validation, protected-wrapper authority and local attachment contract for explicitly enrolled single-project workers. The operator provisions and updates the private companion through existing authenticated Git access; runtime validates the enrolled repository, pointer digest, revision and actor access before exposing it at the declared ignored local path. No secret bytes belong in public configuration, prompts, diagnostics or artifacts. Keep credentials unavailable by default to projects without explicit enrollment.

## Acceptance

- Enrolled single-project Darwin/Evo tasks receive the declared companion under local/ for both Codex and Claude, including continuation/recovery validation.
- Reuse the existing workspace companion implementation rather than creating a second credential authority.
- Only protected operator configuration can authorize the companion; project/source/manifest/repository/revision/path and wrapper ownership checks reject mismatches and redirection.
- Credential enrollment participates in continuation binding so it cannot silently change in a saved invocation.
- Setup documentation includes private authenticated Git provisioning, readable owner-protected permissions, list/doctor/trusted injection checks, rollout at verified idle boundaries and rollback. No project-specific keys or account details in public Morpheus.
- Focused synthetic tests prove normal setup/use, both provider paths, absent enrollment, wrong pointer/project/revision and resume tampering; preserve existing workspaces and private-input behavior.
