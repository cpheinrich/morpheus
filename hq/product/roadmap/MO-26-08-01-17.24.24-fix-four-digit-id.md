## Context

One item kept a four-digit year: `MO-2026-08-01-23.03.19`. It was created between the format
landing and the migration, and it could not be renamed at the time because **its branch encoded
its id** — `check pr` derives the id from the branch name, so changing the id would have made that
PR fail its own conventions check.

`pm migrate-ids` cannot fix it either: the item is already dated, so the migration skips it. It
would have stayed four-digit indefinitely.

Its status was also still `review` against a merged PR, which `pm claim`'s reconciler corrects.

## What changes

`MO-2026-08-01-23.03.19` becomes `MO-26-08-01-23.03.19` — the id, the filename, and the one
generated index link into it. Every roadmap id across all six repos now shares the same
`PREFIX-YY-MM-DD-` shape.

## On the regex

`ROADMAP_ID` still accepts a four-digit year. Nothing produces one now, but branch names outlive
formats and `check pr` resolves ids from them, so rejecting the shape would make an old branch
unresolvable to buy tidiness in a pattern nobody reads.

## Test plan

The full suite, `pm validate`, `pm index --check`, and a check that no relative markdown link
across `hq/` and `.agent/` is left broken beyond the 19 that pre-date the migration.
