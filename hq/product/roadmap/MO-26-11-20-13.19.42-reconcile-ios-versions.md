## Context

When an iOS version goes live, its Xcode marketing version can still be the one the delivery job is about to archive. The release workflow needs an early comparison with the publicly distributed version and an exact next-version proposal.

## Approach

Use a reusable App Store lookup and Xcode version planner before release work starts. Keep GitHub write authority with each project's existing release owner, review and merge. The default version bump increments only the patch component. A deliberate higher bump must name the component. Reset the checked-in build number to zero and keep archive build allocation version-specific in App Store Connect.

## Acceptance

- An equal live/store and Xcode version produces a patch proposal (`1.0` to `1.0.1` and `2.1.2` to `2.1.3`).
- A candidate already ahead continues. An invalid, unavailable or ahead-of-source storefront result prevents an automatic rewrite.
- A rewrite changes only the intended Xcode version/build settings and resets them in one file write.
- The reusable nightly workflow can use the check before release testing or archiving. Existing unconfigured callers retain their delivery contract.
