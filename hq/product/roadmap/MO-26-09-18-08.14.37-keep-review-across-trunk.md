## Context

A cleared review went stale whenever `main` moved, because branch protection requires the PR to
be up to date and the contract let only the worklog change after `covered`. #253 exempted verified
documentation-only merges; code arriving from trunk still forced a reviewer turn or a human, and
three PRs stalled on it (#236, #238, Evo #242 via #245). Chris decided on 2026-09-18 that merging
`main` never invalidates a review, as on a human engineering team: the gate is already a large step
up from no review, CI must still pass on the integrated result, and it can be tightened later if
it leaks.

## Approach

`check pr` walks the first-parent commits the reviewer did not clear. A two-parent merge whose
second parent is trunk and whose tree Git's own `merge-tree` reproduces exactly is accepted with
no record entry. A hand-resolved merge is accepted only when the record's `trunkIntegrations`
names the commit and its reason, so the unreviewed resolution is visible. A merge of anything but
trunk, or a plain code commit, still invalidates. The recorded base need only be trunk history
behind the PR's merge base. The 2026-09-16 documentation-only proof is retired; its field is still
parsed. Rebasing after review is documented as unsupported.

## Acceptance

- A cleared PR that merges new trunk code with no conflicts passes `check pr` with no new turn and
  no record change.
- A conflicted merge fails until `trunkIntegrations` names it, then passes.
- A plain code commit after coverage, or a merge from a non-trunk branch, still fails.
- Records carrying `documentationIntegrations` still parse.
