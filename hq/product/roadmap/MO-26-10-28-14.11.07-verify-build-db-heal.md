## Context

MO-26-10-13-17.05.11 (PR #395, issue #394, shipped 2026-10-13) made `ios-ci.yml` run
`PRAGMA quick_check` on a cached `XCBuildData/build.db`, discard only `DerivedData/Build` when it is
corrupt, and retry a build once cold on a build-service error. Profiling round 2
([worklog](../../../.agent/worklog/2026-10-28-profiling-round-2.md)) still attributed 14 of 25 Evo iOS CI failures between 10-13 and 10-17 to
shared DerivedData `build.db` corruption, and none since 10-18.

That is consistent with the heal working, but equally with Evo picking the change up late, or with
the failures stopping for another reason (runner or slot changes, native builds moving to the CD V2
path). A shipped item is never looked at again, so this item closes the loop.

## Approach

- For each of the 14 failures, establish whether the run used an `ios-ci.yml` revision containing
  #395 (consumers call it at `@main`, so the run's resolved workflow SHA answers it) and which
  runner and slot it ran on.
- Search Evo runs since 10-13 for the heal's own log lines — the corrupt-database discard and the
  cold retry — to see whether it fired and recovered.
- Check whether CD V2's native build path runs the same prepare step; if it does not, it has no
  heal.
- Watch until 2026-11-11. Close with the evidence if nothing recurs; if corruption recurs on a run
  that had the fix, convert this into a defect with the run IDs.
