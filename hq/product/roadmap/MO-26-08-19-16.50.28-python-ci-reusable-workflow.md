## Context

§18's table says CI logic belongs in a reusable workflow, referenced by ref, because the test —
*if I improve this, do I want every existing project to get the improvement?* — is unambiguously
yes for CI. Every workflow that ships today serves a Node surface: `node-ci`, `web-ci`,
`firebase-tests`. A project with a Python surface has nothing to delegate to and writes its own.

Lakina is that project. `apps/backend` is a uv-managed trading system, and its CI job is thirty
hand-written lines doing what `node-ci` does for the other half of the same repository — install a
toolchain, pin a lockfile, lint, run a matrix. It was written by copying a workflow from somewhere
else, which is exactly the outcome §18 exists to prevent, and none of the improvements made to
`node-ci` since have reached it.

This was found while auditing that repository's Python test coverage
(`LK-26-08-19-16.42.42`). Adding coverage there meant either editing thirty local lines or
noticing that the gap is upstream. It is upstream: `heinrich.money` and any future Python surface
will hit it in the same order, and each will solve it privately and differently.

## Approach

`python-ci.yml`, deliberately readable side by side with `node-ci.yml` — same input names where the
concept is the same (`working-directory`, `run-lint`), same single `check` job, same comment
register.

Three decisions worth stating, because each has a tempting wrong answer:

**Coverage is off by default, and its threshold is 0 when on.** A project without `pytest-cov`
installed would fail on an unrecognised flag rather than on its own tests, so the flag cannot be
unconditional. And a threshold shipped as a default is a number picked before anyone measured —
the repositories that fail it on their first delegation learn to lower it, which is how a gate
stops meaning anything. Reporting first, gating on a number the project has actually seen.

**`coverage-source` is required when coverage is on.** Bare `--cov` measures every imported
module, so the reported figure describes the dependency tree. That is not a smaller mistake than
no coverage — it is a number somebody puts in a README.

**`fail-fast: false` on the interpreter matrix.** Whether 3.13 fails too is a fact worth having
about a 3.12 failure, and cancelling the sibling turns a two-line answer into a second CI run.

Tested in `tests/workflows.test.ts`, alongside the existing workflow guards, and verified by
breaking the workflow and watching the tests fail rather than by watching them pass.

Lakina's `apps/backend` is the first caller. Its two release-policy gates — an execution
authorization gate and a cloud-contract validator — stay in its own repository rather than
becoming inputs here: a shared workflow that runs arbitrary command strings supplied by its caller
is a shell runner with a YAML interface.
