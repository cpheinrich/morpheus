# Run portable repository-owned schedules

## Outcome

`src/scheduler/` adds `morpheus scheduler tick | status | admit`, the
`.github/actions/scheduler-admit` composite action, an empty `.morpheus/schedules.json` for
Morpheus, and the contract in `docs/runbooks/scheduler.md` and `architecture.md` §7.15.
`.github/workflows/schedule.yml` lost its hourly cron on Chris's instruction and stays manual.
Croner 11.0.0 is the one new runtime dependency (exact pin, zero dependencies).

## Design choices made while building

- **Activation baseline** is the committer date of the last commit touching
  `.morpheus/schedules.json`. Simplest available fact; the cost is that editing the registry forgoes
  catch-up of slots due before the edit. Documented.
- **Backup probes from the newest slot past grace**, not the latest slot. First test run showed the
  naive "latest slot older than grace" rule can never fire for a `*/5` schedule.
- **Backup within grace reports `waiting`**, not `accepted`: an earlier draft said "accepted" when
  only an older slot had a run, which misdescribed the due slot.
- **Primary keeps its last submission in the status file.** Without it, a confirmed dispatch whose
  run is not yet listed would be resubmitted a minute later. A lost response waits five minutes,
  then resubmits; the receiver guard absorbs the duplicate.
- **Workflow source check before dispatch.** The tick refuses a workflow file with no
  `run-name:` line containing `[schedule:` or lacking either input name, because such runs are
  invisible to history and would be dispatched every minute.
- **Admission marker is a consumer step named `Scheduler occurrence admitted`.** Steps inside a
  composite action are not listed by the jobs API, so the action cannot mint its own marker. The
  first draft used `Scheduler admission` as the marker; root's integration contract gives that
  name to the outer guard step (which succeeds for duplicates too), so the marker was renamed and
  only it is read. The guard refuses to run if its own in-progress step carries the marker name.
- **Lock takeover by owner liveness.** The first draft stole any lock older than ten minutes, but
  a tick has no overall time bound, so a slow live tick could be overlapped. The lock now records
  the PID and is taken over only when `kill(pid, 0)` reports ESRCH; age applies only to a lock with
  no readable PID. Tests cover an hour-old live owner, a dead owner, the ten-minute unowned
  boundary, and a real exited child process.
- **Lock owner identity (core review SCHED-1).** PID-only liveness never recovered a lock left by
  a shutdown once an unrelated process reused the PID after reboot. The lock now records
  `{pid, bootAt, startedAt}`; the owner is running only on the same boot (±2 min), with the PID
  alive, and with the PID's current process started at the recorded time (`ps -o etime=`, ±2 min).
  Unreadable `ps` falls back to the PID, refusing rather than overlapping. Considered a heartbeat
  lease: rejected, because host sleep stops heartbeats and would let a waking tick overlap its
  resumed owner. Tests: six-hour-old live owner refused (with and without `ps`), earlier boot with
  a live reused PID recovered, same-boot reused PID and dead PID recovered, both tolerance
  boundaries, and the real probe against this process (the overlap test uses the real probe).
  Four mutants of the identity checks each killed.
- **Backup acceptance at exactly the probe slot counts** (`>=`). Regression: 15-minute cadence,
  13:22 accepted, 13:37 missed → 13:52 waits, 14:07 dispatches 14:07.
- **Folded run-name.** Every consumer writes `run-name: >-` with the expression on the following
  lines, and the first gate (`/^run-name:.*\[schedule:/m`) refused them all. `runNameOf` now reads
  a top-level flow value or a folded/literal block up to the next unindented line; no YAML parser.
- **iOS nightly baseline (Kairos review KAIROS-1).** `ios-nightly-build.yml` took the head of the
  newest successful caller run as its upload baseline. A duplicate admitted-away run also succeeds,
  so it would have moved the baseline to a commit never uploaded and skipped it forever. The step
  now walks up to 100 successful runs (newest first) and their jobs across all attempts, and takes
  the first whose `upload` / `Upload TestFlight build` / `… / Upload TestFlight build` job
  succeeded. Unreadable runs or jobs build conservatively, as before. Tests execute the real step
  against fixture history through a fake `gh` that applies the step's own `--jq` with real `jq`.
- Croner's `previousRuns` is exclusive of its reference; `slotAtOrBefore` adds one second to make
  "a slot at exactly now is due" true. Mutating that away fails two tests.

## Real-environment probes (read-only)

- Disposable copy of the tracked tree, `npx --yes pnpm@11.9.0 install --prod --frozen-lockfile
  --ignore-scripts` → exit 0, `node_modules` held only the nine production packages including
  croner. `scheduler status` printed `no tick has written a status yet`; `scheduler tick
  --dry-run` against `cpheinrich/morpheus` (no registry on main yet → isolated error) and a
  nonexistent repository (404 → isolated error) used the injected `GH_TOKEN`, wrote no status file.
- Direct client reads against `cpheinrich/morpheus`: workflow-runs pagination with the `created`
  filter (0 dispatch runs in 6h), `schedule.yml` workflow state `disabled_manually` (already off in
  GitHub), commit-date lookup, and the jobs API shape (`run_attempt`, step `name/status/conclusion`).
- No dispatch was submitted anywhere.
