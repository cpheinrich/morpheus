# MO-26-10-31-06.49.52 — same-provider gateway delegates

## What happened

A new Claude session reported routing to the Codex gateway (53% used) "most headroom" while
the Claude gateway sat at 0%. The router filtered out the coordinator's own provider
entirely. Chris clarified that the gateway is a separate subscription and a valid delegate;
only the coordinator's own native login is circular. Implemented for both directions.

## Live check (2026-10-31, gateway on zoe-mac-mini)

From this Claude session, with this Mac's Claude CLI logged out: `codex.inspect` routed to
`claude gateway (claude) at 0% used`; `codex.start` launched a Claude worker
(`executor: claude`, `gateway: claude`, the session's `auto` mode and `claude-opus-5-5`)
that completed a read-only task with the right answer. sub2api's `claude-max` account
`last_used_at` moved to the run's time. No configured secret value appears in the run files.

Observed, not changed: sub2api's `codex-pro` `last_used_at` and Codex usage fields stayed at
01:32 despite gateway Codex runs at 06:2x–06:41, so Codex gateway quota may be stale until
sub2api refreshes it.

## Found while testing

The first end-to-end test showed a worker inheriting the variable an `env:` admin reference
names (the admin password). Real installs here use `exec:` references, but `env:` is
documented, so every variable a configured reference names is now removed from worker
environments.

## Tests

`node scripts/check.mjs`; `pnpm test` in `plugins/factory`: 133 pass. New: routing rules for
own-provider gateways and overrides (`config.test.mjs`), and `gateway-workers.test.mjs`,
which runs the real guardian with fake CLIs and a stubbed sub2api API for a Claude session →
gateway Claude worker (live question answered through `codex.answer`) and a Codex task →
gateway Codex worker (full-access and read-only sandboxes, per-gateway session resume).

## Review

One fresh reviewer turn, blocked with a condition that cleared both substantive findings.
It verified that routing never chooses the coordinator's own native login, that
same-provider workers never widen permissions, that sessions resume only on their own route,
and that the `codex.answer` cross-session guard holds. F01: the new secret scrubbing deleted
the selected route's key when its `keyRef` named the provider's own variable
(`env:OPENAI_API_KEY`), which could fall back to native credentials. F02: the
Codex-coordinated path lacked the same-route check on a `needs_input` reply that the README
promises. F03 (minor): the refusal should name the original route. All three fixed in
d2d5cb5a; evidence from `plugins/factory`: `node scripts/check.mjs`, `node --test
tests/gateway-workers.test.mjs tests/config.test.mjs` (20 pass), and the full suite (134 pass).

Two substantive findings (secret scrubbing could delete the route's own key; the Codex-coordinated reply path lacked the same-route check) fixed under the reviewer's condition, plus one minor message fix. Routing never delegates to the coordinator's own native login, permissions never widen, sessions stay on their route and the answer guard holds.
