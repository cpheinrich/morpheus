# MO-26-10-05-23.14.22 — GitHub Manager trusts authors by repository permission

## What happened

The manager's first live run on Evo (ops run 37422417014, 2026-10-05) routed nine open pull
requests. Seven were Chris's, and all seven were skipped as `untrusted-author`: the App saw him as
`CONTRIBUTOR`. With a user token GitHub reports the same pull requests as `MEMBER`, and Chris has
admin on the repository. His `darwin-health` membership is private; Robbie's is visible, and
Robbie's pull requests were trusted correctly. `author_association` is computed from what the
reader can see, and an installation token cannot see private membership.

## What shipped

`fetchAuthorPermission` reads `/repos/{repo}/collaborators/{user}/permission` only when the
association does not already establish trust. `admin`, `maintain` and `write` are trusted; `read`,
`triage`, absent and unreadable are not. Forks stay refused whatever the permission.

## Evidence

- `tests/gh-manager.test.ts`: the hidden-association case for each trusted permission, `read`,
  `triage` and an unreadable permission refused, a fork with admin refused.
- Not verified against the real App token yet: its key exists only as an operations-repository
  secret. The next scheduled run is the verification, and it should route Chris's pull requests
  past the trust check.

## Also learned on that run

The Claude sessions failed on their first request with `401 OAuth access token is invalid`; the
stored token was malformed. Both sessions failed closed: apply posted a "no decision" comment on
each pull request, counted the attempt, and changed nothing else. That is the behaviour the design
asked for, now observed rather than only tested.
