# MO-26-10-13-17.05.11 — Self-heal a corrupt shared DerivedData build database in ios-ci

Issue #394. Evidence: darwin-health/evo run 38486385137 cancelled at 23:47:44Z on 2026-10-13,
run 38486255994 started on the same cache slot at 23:47:48Z and failed in `Build for testing`
on `XCBuildData/build.db` ("no more rows available", then "database disk image is malformed",
then "internal inconsistency error" for every package target); run 38487005844 failed the same
way on that slot six minutes later. Slots have separate cache disks, so this is a killed
`xcodebuild` leaving SQLite mid-write, not two VMs sharing DerivedData.

## Change

- `ios-ci.yml` "Prepare isolated build directories": `sqlite3 -readonly build.db 'PRAGMA quick_check'`
  on a cached build database; anything but `ok` removes `DerivedData/Build` with a warning.
  Module cache and package checkouts are untouched.
- "Build for testing" and "Build": on failure whose log matches `accessing build database` or
  `internal inconsistency error`, remove `DerivedData/Build`, keep the failed log as
  `build-damaged-cache.log` and the first attempt's result bundle as `Build-damaged-cache.xcresult`
  (xcodebuild refuses an existing `-resultBundlePath`), and build once more. Any other failure
  exits with xcodebuild's own status; a second build-service failure is a real failure. The job
  declares no `shell:`, so GitHub runs these steps with `bash -e {0}`; the retry branch's moves
  are therefore fatal on CI if they fail, which is intended.
- `tests/ios-build-cache.test.ts`: runs the real step scripts with stub `sqlite3`/`xcodebuild`:
  damaged database discarded (only `Build`), healthy kept, no check without a cache, one retry
  on a build-service failure for both build steps, no retry on a compile error, second failure
  propagates.
