# MO-26-10-04-16.24.17 — Relaunch the test host when iOS CI retries a failed test

## Why

Evo's release lane (which calls this workflow through `ios-nightly-build.yml`) lost two of its
last seven runs, on 1 and 3 October 2026, to a StoreKit purchase that the simulator's ledger
daemon stopped answering. After the first `Product.purchase()` failed, every retry of the four
affected tests failed in about 150 ms, all twelve failed executions carried the same pid, and
the release was blocked for a day each time. `-retry-tests-on-failure` reuses the test-host
process, so a failure rooted in the process, or in a daemon's view of it, cannot be retried.

## Change

`-test-repetition-relaunch-enabled YES` is appended next to the existing
`-retry-tests-on-failure -test-iterations "$TEST_ITERATIONS"` pair in the `Run unit and UI
tests` step. `xcodebuild -help` on Xcode 26 documents the flag as requiring exactly one of
those companions. The gate is unchanged: a test failing every attempt still fails the run.
Evo's `apps/ios/scripts/dev.sh` has passed the same pair for `TEST_REPETITIONS` since September.

## Evidence

- `ruby -ryaml` parses the workflow.
- `pnpm exec vitest run tests/ios-evidence-workflow.test.ts`: 7 passed, including the new case
  that runs the step at `TEST_ITERATIONS=0` (no retry flags) and `3` (the five entries in order).
- `pnpm lint`, `pnpm typecheck`: clean.
- First real exercise is Evo's next release run after merge; Evo's result-bundle verification
  already handles per-attempt `Repetition` nodes, which is the shape relaunch mode produces.

## Independent review

A fresh Claude review at small risk read the one-flag change, ran the extracted step against a fake xcodebuild in all three paths, and fed a real relaunch-mode result bundle through Evo's evidence scripts to confirm attempts keep the same shape. It cleared the change with one minor finding, that the workflow harness never exercised the retry flags; the author added that case under the minor-only allowance and no second turn was needed.
