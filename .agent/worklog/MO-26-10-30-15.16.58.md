# Retry iOS tests in a fresh simulator

**Ask.** Evo's CD calls `ios-ci.yml` with `test-iterations: 3`. Those retries ran in the same
simulator and xcodebuild session, so a UI test broken by state an earlier test left behind failed
all three iterations; four of six Evo delivery test-job failures since 2026-10-20 had that shape.
Chris's direction: checks that protect users block, everything else warns; simplify instead of
adding machinery; production differs from staging only by running more tests.

**What was built.** `scripts/ios-test-retry.py` (standard-library Python, run by the test step)
runs the caller's selection once. On failure it erases the job-owned simulator in place, reruns
the caller's pre-test script with `RESULTS`/`LOGS` at `attempt-<n>/`, and starts a new serial
xcodebuild with `-only-testing` of the still-failing identifiers and `-collect-test-diagnostics
never` where Xcode has it. A pass on a clean retry is flaky: warning annotation, job-summary line,
`flaky-tests` JSON output on the job and the workflow; a test failing every attempt fails the job.
A failure that names no test, an exit status contradicting all-passing results, and a test missing
from a retry's results all fail rather than pass. `test-iterations` keeps its name, now attempts in
total, default 3 (nightly forwards the same default). Scope is the existing `test-plan`,
`only-testing` and `skip-testing` inputs, now documented as the staging-smoke/production-full
lever. `test-attempts.json` records every attempt beside the first attempt's `Tests.xcresult`.

**Midway change.** The coordinator reported that Evo's PR CI now calls `ios-ci.yml@main` (with
`actions-ref: main`) and that this change goes live for Evo on merge. Evo's `verify-results.mjs`
requires every test in `tests.json` to pass and `summary.json` to pass, which in-process retries
satisfied (a recovered test read as `Passed` with `Repetition` children). Left as attempt 1's raw
export, a test cleared by a fresh retry would pass the test step and then fail Evo's validator: a
regression. So when the retries recover every failure, the script writes `tests.json` and
`summary.json` in that same shape, and the export step keeps them. Checked against Evo's own
`resultTests` on the real Xcode 27 bundles: the recovered test reads `Passed` with attempts
`["Failed","Passed"]`, and the summary passes its check. Evo's `prepare-unit-device-policy-tests.sh`
and `prepare-tests.sh` only write under `$RESULTS`/`$LOGS`, so they work per attempt unchanged.

**Result.** Verified for real on this Mac (Xcode 27.0, iOS 26.5 simulator) with a fixture whose
second UI test fails after an earlier launch in the same simulator: attempt 1 failed it, the retry
in the erased simulator passed it, the job exited 0 with the warning, summary and output. With an
always-failing unit test added, that test failed all three attempts and the run exited 65 while the
UI test was still reported flaky. The first run exposed a real bug no fake would have:
`xcodebuild -help` prints to stderr, so the diagnostics flag was never detected; fixed, and the
fake now matches. The actual reusable workflow, run twice on a GitHub-hosted macOS runner, behaved the same (Appendix A).

**Dead ends.** `xcresulttool merge` of a failed attempt and its passing retry reports the test as
`Failed` (two `Repetition` children), so merging cannot give consumers Xcode's "passed after retry"
view; the first attempt's bundle stays the evidence and `test-attempts.json` carries the verdict.
Retrying several failed tests in one invocation can still share state between them (the first
fixture did exactly that: a hosted unit test relaunched the app before the UI test); the brief asks
for one invocation per attempt, so that is accepted.

**Open for the consumer.** Evo's PR CI takes this on merge (`@main`, `actions-ref: main`, already
`test-iterations: 3`). A caller that pins the workflow must pin `actions-ref` to the same commit;
the step fails with a named error otherwise. Staging smoke versus production full is `only-testing`
or a smoke `test-plan` versus neither; Evo's `prepare-tests.sh` asserts empty `ONLY_TESTING` in full
scope, so a staging smoke scope needs its own case there. On Xcode 27 a failing first attempt can
still wait 600 s collecting diagnostics (one of two local failing runs did, and collected nothing),
because the brief scoped `never` to retries.
