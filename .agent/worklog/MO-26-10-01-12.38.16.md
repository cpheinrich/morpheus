# MO-26-10-01-12.38.16 — GitHub Manager

A scheduled agent that sweeps open pull requests and lands the ones that stalled. Design and
operations are in `docs/runbooks/gh-manager.md`; this is what was learned building it.

## What the pile-up actually was

Measured on 2026-10-01 before designing anything: 20 open pull requests across Evo (11), Lakina (6)
and Morpheus (3). Thirteen failed `pr / conventions`. In the logs sampled the cause was a missing
`agent-reviewed` label (three) or missing visual evidence (one). So it was never mainly "nobody
clicked merge": the authoring session had ended before the review loop did. Three more had no
failing check and simply never had auto-merge enabled, which is why the sweep does that without a
session.

## What shipped

- `src/gh-manager/`: policy schema, the deterministic sweep, the session brief, decision checks,
  the `gh` layer and the run digest. `morpheus gh-manager sweep|routes|prompt|apply|digest`.
- `src/review/manager.ts`: the `morpheus-manager-review` record and its check, selected by the
  `manager-reviewed` label. `pr-check.yml` reads who applied that label from the issue events.
- `.github/workflows/gh-manager.yml`: sweep, session and apply as three jobs with three tokens.

## Decisions made while building

- **A separate record, not a fourth turn.** The first design reused `humanAuthorization` or added
  a `managerAuthorization` turn to the existing record. Chris's correction was that the manager is
  itself the fresh session and must fix its own findings, because nobody answers a review handed
  back to an absent author. That does not fit a record whose every rule assumes an author and a
  distinct reviewer, so it is its own fence with its own, smaller validator.
- **The label's actor is the guard.** A manager record is easy to write by hand. What an author
  cannot do is apply a label as `morpheus-gh-manager[bot]`, so `check pr` requires that actor and
  treats an unreadable one as a refusal.
- **Apply runs on a different runner from the session.** Steps in one job share a user, so a
  process a session left behind could read a later step's environment. A job boundary is a fresh
  machine.
- **The pinned Claude Code CLI, not `claude-code-action`.** The action reads the calling
  repository's event context, and this workflow is called from the operations repository while
  working on another one.
- **A cancelled check is rerun, not treated as a failure.** Nothing about the change was judged,
  and a required check left cancelled holds auto-merge open forever. Evo #290 was in that state.

- **The label alone was not enough; the clearance is bound to a head.** The independent review
  showed that once the App had labelled a pull request, its author could push more code and
  rewrite the record to cover it, and every check would pass. The App's comment now carries the
  head it cleared, `pr-check.yml` reads that from the App's comments, and nothing may follow it
  but exact trunk merges.
- **The session's token has no `workflows` permission.** It was granted at first so that a merge
  from trunk carrying a workflow change could be pushed. That same permission let a session edit
  the checks that judge it. Withholding it makes GitHub refuse such pushes; a refused trunk merge
  is an escalation.
- **Apply verifies with Git, not with the decision file.** It checks out the target and reads what
  the session pushed and whether its record validates, using the functions `check pr` uses.
- **The comment goes first.** It carries the marker, so a plan that fails half-way still counts as
  an attempt, and the label event that re-runs `check pr` finds the clearance already there.

## Dead ends

- `check pr` cannot be run by a session on a runner with the documented local overrides:
  `GITHUB_EVENT_PATH` is set there and wins over `MORPHEUS_PR_BODY`, returning an empty body. The
  brief clears it for that one command.
- GraphQL reports an App's login without `[bot]` in some fields. Every identity comparison uses
  REST for that reason.

## Evidence

- `tests/gh-manager.test.ts` (36), `tests/manager-review.test.ts` (14) and the `gh-manager.yml`
  group in `tests/workflows.test.ts`.
- A read-only sweep against Evo's eleven real open pull requests routed #290 to `merge`, four to
  `session`, and skipped the rest as active or already queued.
- **Not yet verified against the real thing at the time of this commit:** the session and apply
  jobs have not run in GitHub Actions. The first Evo run is the verification, and is recorded in
  the pull request.

## Independent review

One fresh reviewer session reviewed f983518 at high risk and blocked it on three substantive findings: the manager-reviewed label was not bound to a commit, model-written text could forge the manager's marker, and the session token could do more than the design claimed. All three and seven minor findings were fixed in fbdd66f, and the same reviewer cleared that commit in one follow-up turn; the residual that contents write is repository-wide is documented and left for Chris to accept.

Three things the reviewer could not verify and that the first Evo run must: that the `pr-check` job token can read issue events and comments on a private repository, that GitHub refuses a workflow-file push without the `workflows` permission, and whether a trunk merge carrying workflow changes can be pushed without it. The first two fail closed. Two non-blocking observations are left as they are: an escalation whose label removal fails part-way leaves the earlier clearance valid for that head, and under `sessionBeforeMerge` a manager-cleared pull request whose head moved by a trunk merge is escalated rather than re-cleared.
