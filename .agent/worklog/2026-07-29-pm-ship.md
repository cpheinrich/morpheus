## How it surfaced

Not from a bug report. From reading the roadmap index while deciding what to work on next, and
noticing that thirteen things I knew were merged still said `review`.

Worth naming: **the board was wrong for two weeks and the only reason it got caught is that
somebody read it for a different purpose.** Every status transition in the system was automated
except the last one, and the last one is the one that makes the board true.

## The design point

The claim model already had the answer — the remote branch *is* the claim, merging deletes it, so
a review item with no branch has almost certainly shipped.

**Almost** is doing real work in that sentence. A missing branch is the absence of evidence, not
evidence of a merge. So `mergedPrs` returns `null` when `gh` is unavailable rather than `[]`, and
reconcile writes nothing in that case. Collapsing those two would make a missing tool look like a
clean board — the same failure as reporting GCP ids "taken" by grepping for `^ERROR`, which is
already in `.agent/learned.md`. That is twice now; the pattern is **never let an unanswerable
question render as a confident answer.**

## What it found

Eleven items promoted. Then the one I did not expect: **PR #1 merged without deleting its branch**,
so `mo-017-branch-protection` still sat on origin and MO-017 read as claimed. `pm claim MO-017`
would have refused forever with a message pointing at a branch nobody was working on.

That got its own outcome type rather than folding into "open". A false claim blocks work; a stale
status only describes it wrongly.

## Left undone deliberately

Automating this on merge needs writing to protected `main`, which is a real decision rather than a
detail. For now it is a command, documented in AGENTS.md next to the merge step.
