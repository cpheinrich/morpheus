# 2026-08-02 — goal ids that the schema accepts

MO-26-08-02-15.15.21

## How it surfaced

Not from working on Morpheus. Scaffolding a new project (Heinrich LLC), first command after
`morpheus init`:

```
$ morpheus pm new goals "Heinrich LLC can take on a new project in a day"
Created .../hq/product/goals/HL-G-001.md
✗ Goals — fix validation issues first
    id: must look like EV-G-2026-Q3-01     (x6)
```

The tool writes a file and then tells you the file is wrong. Worth noting that the *reporting*
made it look worse than it was: six identical lines for one file, because `pm validate` prints
per failed check rather than per file. For a moment it read as six broken goals.

## Two defects, three lines apart

1. `nextId` builds `${prefix}-${INFIX[kind]}${nnn}` for both goals and requests. Right for
   `FR-007`, wrong for goals, whose `GOAL_ID` carries the period.
2. `period:` was `` `${date.slice(0, 4)}-Q1` ``. Hardcoded. Written in August, filed under Q1.

Same root cause: nobody had decided *where* a goal's period lives, so it was half in the schema
and half nowhere.

## The interesting part — why 554 green tests said nothing

`tests/pm.test.ts` asserted `MO-G-039`, `MO-G-041`, `MO-G-001`. Those tests are not wrong about
what the code does; they restate it. The generator was consistent with itself, the schema was
consistent with itself, and no test ever put a generated goal in front of the validator.

So the rule for this file going forward: **an artifact test asserts through `parseArtifact`, not
against the string the generator produced.** The generated id is an implementation detail; the
thing worth pinning is that the file parses. That is now how the goal test reads, and it fails
against the old code.

Morpheus's own `MO-G-2026-Q3-01.md` is correctly shaped — because it was typed by hand. Every
goal the CLI has ever produced was invalid, and the only reason that never bit is that goals are
rare enough that Chris wrote the one that exists.

## Dead ends

- **Loosening `GOAL_ID` to accept `MO-G-001`.** Cheaper diff, wrong direction: the period is the
  most useful thing in a goal id, and `--goal G-2026-Q3-01` in the CLI usage means the periodful
  form is what the rest of the system already expects.
- **Deriving the period inside `createItem` from `date.slice(...)`.** That is the bug, one layer
  up. The quarter has to come from the same `ZONE` the ids use or it drifts near a boundary —
  31 December, 4pm Pacific, is Q4 in Pacific and Q1 in UTC.

## Not changed

`claimedNumbers`. The longer prefix lowercases to `mo-g-2026-q3-` and the existing
`^prefix(\d+)-` pattern still separates a goal branch from a request branch. Checked rather than
assumed — the doc comment on `parseClaimedNumbers` is specifically about that confusion.
