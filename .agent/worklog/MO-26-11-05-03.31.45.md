# Release preflight accepts a protected iOS release-branch source for an opt-in caller

## Outcome

This is the Morpheus half of Evo's branch-first releases with grouped UI remediation
(EV-26-11-05-03.33.54). It is a draft PR only: Chris asked for both halves to stay unmerged.

- **`release-preflight.yml`.** Three new opt-in inputs: `release-branch`, `release-base` and
  `source-sha`. All default to empty, and with them empty the workflow takes exactly today's path.
  With any of them set, a new step checks the following. Any failure refuses with a message naming
  the condition, and an unreadable API answer refuses rather than passes.
  - All three inputs are set and well formed.
  - The branch is named `release/ios-<base[:12]>` and is protected.
  - The base is contained in `main`.
  - The source is the branch tip or an ancestor of it, and the base is an ancestor of the source.
  - Every commit from base to source is the merge commit GitHub recorded for a merged PR into that
    branch, with at most 250 commits.

  The verified commit is published as a new `source-sha` output. The control commit check and the
  `sha` output are unchanged.
- **`ios-ci.yml`.** The evidence export also writes `Results/environment.json`: macOS, Xcode,
  simulator runtime and device type, runner, and the Morpheus refs. Any value it cannot read is
  `null`, and the step never fails the run. Evo's planner refuses to carry a passing test across
  environments that differ or cannot be compared.

## Design choices

- **The check is squash lineage, not first-parent merges.** Evo repairs are squash-merged into the
  release branch. So the check is that each commit in `compare base...source` is some merged PR's
  `merge_commit_sha` with `base.ref` equal to the branch. A direct push has no such PR. A PR merged
  into `main` has the wrong base. A merge commit's own parents are not anyone's `merge_commit_sha`.
- **The environment is read from files, not by calling `xcodebuild`.** The first version called
  `xcodebuild -version`, which overwrote the evidence tests' fake `xcodebuild` argument log. Reading
  `$DEVELOPER_DIR/../version.plist` avoids running the tool at all.

## Dead ends

- The fake GitHub API routes were first keyed on a fixed source SHA. As a result, the "base as
  source" accept case hit an unrouted path and failed for the wrong reason. The routes are now
  derived from the `SOURCE_SHA` under test.
- `${ACTIONS_REF_INPUT}` under `set -u` aborted the evidence step in tests where the input was absent.
  The fix is `${ACTIONS_REF_INPUT:-}`.

## Validation

- `pnpm exec vitest run tests/workflows.test.ts tests/ios-evidence-workflow.test.ts`. The release-branch
  cases run the real step script against a fake `gh`: one accept, a base-as-source accept, 11 refusals
  and a half-specified refusal.
- `pnpm typecheck`, `pnpm compile` and `pnpm morpheus pm index`.
- The full suite was not run locally. No shared core (`src/pm`, `src/check`, `src/session`,
  `src/review`, `src/init/templates.ts`) changed; CI runs it.
- Natively, Evo's Mini qualification ran `scripts/ios-test-retry.py` from this checkout. It did not
  run `ios-ci.yml` on a hosted runner, so the `environment.json` step was exercised only by the
  workflow tests.

## Open

- No live caller opts in yet. Evo's delivery wiring of these inputs is the next step on the Evo side.
- Branch protection or a ruleset for `release/ios-*` in Evo is documented, not applied.
