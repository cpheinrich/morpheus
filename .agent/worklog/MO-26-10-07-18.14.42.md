# MO-26-10-07-18.14.42 — python-ci: choose the runner

- Request: Lakina wants backend CI on a self-hosted Linux VM runner (`linux-vm`) with GitHub-hosted
  `ubuntu-latest` as the fallback. `python-ci.yml` hardcoded `runs-on: ubuntu-latest`.
- Change: a `runner` string input (default `ubuntu-latest`, one label, not JSON) on `python-ci.yml`,
  `node-ci.yml` and `web-ci.yml`, each job using `runs-on: ${{ inputs.runner }}`. Worded as in
  `ios-ci.yml`'s `runner` input. `node-ci` and `web-ci` were an identical one-line change, so they
  were included for Lakina's web surface later. `tests/workflows.test.ts` pins the input's type,
  its default and the `runs-on` wiring for all three; with `python-ci.yml` reverted the python case fails.
- Docs: header example in `python-ci.yml`, and a paragraph in `architecture.md` section on reusable
  workflows saying the caller owns the runner and any fallback.
- Fallback: a reusable workflow cannot retry a job on another runner, so "automatic fallback" is the
  caller's to build (for example a cheap job that probes runner availability and passes its result
  as `runner`). Nothing here supplies it. Recorded in the architecture paragraph.
- Process: the primary checkout was 76 commits behind trunk with someone else's uncommitted change,
  so `context brief` could not certify it. A detached worktree at `origin/main` was made by hand
  in the usual `.morpheus-worktrees` directory, the changed records were read, and `pm new` and
  `pm claim` ran there. The branch it claimed is `mo-26-10-07-18.14.42-python-ci-choose-runner`.
