# CLI output drains through pipes before exit

## Ask (2026-11-05, Chris's complexity rollout mandate, via the Codex CTO controller)

The controller found that `complexity check --json` (PR #625's large per-function JSON) piped into
`json.loads` received exactly 65,536 bytes and failed at character 65,532, while the same command
redirected to a file wrote 83,941 valid bytes. Fix it with the simplest design that keeps exit
codes, the forced exit of ordinary commands and the CD quota/worker cleanup path.

## Cause

`src/cli/index.ts` has ended ordinary commands with `process.exit(code)` since the first CLI commit,
so a command exits even if some handle (a timer, a keep-alive socket) lingers. On macOS Node writes
pipes asynchronously; `process.exit` drops whatever is still queued once the 64 KiB pipe buffer is
full. Files are written synchronously, which is why redirection hid it. The CD quota/worker path
(#554) already sets `process.exitCode` instead, so its owned reader can drain and clean up; that
path is untouched.

## What was built

`finish()` keeps the forced exit but first writes an empty chunk to stdout and to stderr and exits
from the second callback. A write's callback runs only after everything queued before it, so both
streams have flushed. A closed reader calls back with an error (EPIPE), and the CLI then exits with
the same code, silently, as before. About ten lines, Node built-ins only.

Probed first, in a scratch script with a lingering interval (the riskiest assumption: that the
callback fires after earlier queued writes, and that a closed pipe neither hangs nor prints a trace):
old 131,072 of 178,919 stdout bytes through a pipe, new all of them; stderr likewise; `| head -c1`
and `| true` exited with the original code and no EPIPE output.

## Tests

`tests/cli-exit.test.ts` runs the compiled CLI (`pm tagged` over 1,200 synthetic roadmap items,
under a preloaded never-cleared interval) with both streams on real pipes that are not read for
300 ms, and compares with the same command written to files:

- `--json` stdout (646,709 bytes): exact byte count, `JSON.parse` succeeds, all 1,200 items, one
  tail sentinel, exit 0.
- Invalid items (non-JSON mode): 260,400 bytes of stderr, every one of the 1,200 issue lines,
  exit 1.

Against the old `dist/cli/index.js` both fail (65,536 and 131,502 bytes received). Mutants: draining
stdout only fails the stderr test; replacing the exit with `process.exitCode` hangs on the lingering
handle and both fail at the 15 s fuse.

Dead end worth recording: the first version paused the child's streams and attached listeners
later. Node's `child_process` resumes an unlistened stdio stream when the child exits and discards
its data, so the test read 0 bytes even with the fix. Attach the listeners first, then pause.

Node documents pipes as synchronous on Linux, so Linux CI probably passes with or without the fix;
the local macOS runs above are the evidence that the test catches the bug.
