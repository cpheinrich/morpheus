# MO-26-10-06-17.45.09 — Bring a queued pull request up to date when it is behind

## What happened

The manager's first Morpheus run enabled auto-merge on #262 and #322. Both then sat `BEHIND` main:
Morpheus requires branches to be up to date and GitHub's auto-merge never updates one. Every later
sweep routed them to `waiting`, which is the stall the manager exists to clear, reproduced one
level down.

## What shipped

- `behind` on the pull request facts, from REST's `mergeable_state === "behind"`.
- Sweep: a queued, green, non-conflicting pull request that is behind routes to `merge` /
  `update-behind`. Failing or conflicting still goes to a session.
- Plans: every merge ends with `update-branch` (PUT `/pulls/{n}/update-branch` with
  `expected_head_sha`) when behind, after auto-merge is queued. Updating an already-queued pull
  request posts a comment, because it pushes a commit.
- Same approach as the Dependabot maintainer's `shouldAdvanceAutoMerge`.

## Why it is safe

The update is a merge GitHub performs without conflict, which `check pr` accepts after a review
of either kind as an exact trunk merge. It is guarded on the head the plan was made for, so a push
in between makes GitHub refuse rather than merge over it. Pushes made with an App installation
token start CI, unlike `GITHUB_TOKEN`.

## Review findings that changed the design

- **The update may be refused on exactly the pull requests it is for.** The App deliberately has no
  Workflows permission, and both #262 and #322 would bring a `.github/workflows` change in from
  trunk; GitHub refuses a push like that from a token without the permission. This was not
  confirmed live, because the App key exists only as an operations secret. Rather than widen the
  App's permissions, a refusal is now handled: the plan records the head it tried (`updated` in the
  marker), and if the next run finds the same head, GitHub refused, so it escalates once and keeps
  auto-merge queued for when a person merges the base in.
- **A refusal would have repeated every run.** The same record bounds it to one escalation.
- **The manager's own update restarted the quiet window**, so a branch it had just updated would
  sit for eight more hours. Only the update it recorded is exempt: a two-parent head authored by
  the App whose first parent is the head in the marker's `updated`. A session's fix commit still
  counts as activity (exempting it would let the next hourly sweep start another session on
  pending CI), and a commit merely claiming the App's address is not exempt.
- **A refused update keeps the manager's clearance.** Removing `manager-reviewed` would have left a
  pull request that could never land after a person merged the base in, while the comment said
  auto-merge was still queued.
- **Mocked, not live:** that GitHub leaves the head unchanged when it refuses an update is how the
  API behaves, and is what the refusal detection relies on; it has not been observed here yet.

## Evidence

- `tests/gh-manager.test.ts`: routing for behind with auto-merge on and off, merge disabled,
  failing and conflicting; plans for queued, unqueued and session-decided merges; no update when
  not behind; the guard head.
- Live verification is still owed: #262 and #322 on the next run after the pin moves. Either the
  update lands, or it is refused and escalated once. The workflow-file case is the one to watch.
