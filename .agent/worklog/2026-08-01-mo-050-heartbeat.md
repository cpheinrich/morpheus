## The decision that made it shippable

The handoff spec described the assess step as a prompt. I started there and abandoned it inside
ten minutes, because the consequences all point the same way: unrunnable without a credential
(there is none), untestable in CI, dead at the first billing failure, and non-deterministic in a
job that runs unattended twice a day.

Then the obvious question — *what does the prompt actually need to know?* — and every input was
already in git. Priority, goal status, claim age, ceiling headroom. The "highest-leverage unblocked
aligned work" is a sort.

So `assess()` is a pure function of parsed inputs, 33 tests, no mocking, no network. A model can
reorder or veto it later as a second opinion over a ranking that stands alone. **That is the whole
reason this shipped before the credential question was resolved**, which is exactly what asking
about credentials at intake was for.

## Priority before alignment, and why it matters

The ranker could order by goal alignment first. It does not. Priority is a human's explicit
statement of leverage; alignment is derived from a goal link that plenty of legitimate items do not
carry. Alignment-first means a P0 with no goal set sits behind a P3 that happens to name one, which
is the ranker overriding the person.

Explicit signal beats derived signal. Age is the last tiebreak, oldest first, so nothing starves at
the bottom of the board.

## The guard that took the most thought

**Blocked is not in-flight.** A blocked item holds its branch on purpose — the partial work is
there — so the naive reading is that it occupies a lane. But then one unanswered question consumes
a lane until someone answers it, and three of them deadlock a ceiling of three. A ceiling that
cannot be released is not a guard, it is a scheduled deadlock.

This is the interaction that made MO-049 a prerequisite rather than a sibling, and it has a direct
test.

## Two failure modes I only found by asking "what if it lies"

1. **An unreachable origin reads as an empty claim list.** `listClaims` fetches from origin, and a
   network failure would have produced zero claims — which the beat would read as three free lanes
   and dispatch straight through a full ceiling. It now refuses. Same family as `claimedNumbers`
   returning null rather than `[]`, already recorded in `learned.md`.
2. **A shallow checkout does the same thing in CI.** `actions/checkout` defaults to depth 1, single
   branch, so `for-each-ref refs/remotes/origin/` would find nothing. `fetch-depth: 0` is
   load-bearing, and there is a test asserting it is still in the workflow — the kind of thing that
   gets "cleaned up" by someone optimising CI time.

## Drift, found by accident

While deciding what counts as a candidate: an item with `status: in-progress` and no branch on
origin is neither in flight nor available. It is drift, and something already went wrong there, so
handing it to another agent would compound it. The beat reports it instead. Cheap, and it fell out
of the definition rather than being designed.

## Verified against the real board

Not just units. `morpheus heartbeat` against Morpheus's own board picked MO-005 — P1, serves the
live goal, oldest of the P1s — with MO-050 and MO-054 correctly read as in flight, including
MO-054 claimed by a parallel session I did not know about. That last part is the useful evidence:
the claim read is genuinely remote.
