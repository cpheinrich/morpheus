# Diagnose GitHub protection holds and wait for rerun attempts

Issue #723 reported two `wait-ci` gaps. The first: `--required-only` said green while GitHub still
held the PR `BLOCKED`, and the only cause found was an older cancelled run of a required job beside
a newer passing run on the same head. The second: `--run <id>` straight after `gh run rerun`
returned the previous attempt's cancelled conclusion.

**Blocked merge state.** The rollup query now also reads `mergeStateStatus`. When a `--required-only`
wait is green and GitHub says `BLOCKED`, the digest adds a line saying the two disagree. The verdict
and exit 0 stay unchanged, and no merge gate is added. If the rollup holds a required job whose
cancelled run a newer attempt replaced (the rows `dedupe` drops), it lists them with their
`gh run rerun` command as a *possible* cause. GitHub does not say which rule blocks, so the
advisory does not claim this cause. Otherwise it points at reviews, rulesets and required checks
that never reported. Default all-checks waits and failed verdicts print nothing extra. This
follows the scope the handoff asked for: only the required-only result stands for protection.

**Rerun attempts.** `wait-ci --run <id> --attempt <n>` keeps waiting while GitHub reports an
attempt below `n`, whatever its status, until the existing timeout. At the deadline it exits 2
naming the attempt it saw. A later attempt is accepted because `gh run view` reports only the
latest. `--attempt` requires `--run` and a positive integer up to six digits; without it nothing changes.

`usageError` exceeded the CCN limit after the new checks, so its run and workflow checks moved into
two helpers. The `--required-only`-with-a-run check now runs before id validation, which only changes
which message a doubly-wrong command gets. The run-wait stop condition moved into `RunWatch.answered`.
