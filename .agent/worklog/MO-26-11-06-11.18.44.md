# Complexity refactor metrics come from the targeted check

## Ask

Chris: "For the toolkit—is it clear they only need to run the analyzer on changed functions and not
the entire codebase?" Mostly yes — `AGENTS.md`, the template and the runbook's loop all say
`check` after each changed family, and `check` is targeted by default — but the refactoring
prompt v1.5 and the runbook's refactoring section told agents to take before-metrics from
`check --all --json` in a detached worktree at the base. That is a routine whole-repository scan,
and it also mislabels: for code the branch itself wrote, trunk is "before the feature", not
"before the refactor".

## What changed

- `src/complexity/refactoring-prompt.md` → v1.6. The metrics paragraph now says the before side is
  the candidate report (the targeted `check --json` run before editing, saved with its commit,
  dirty state and analyzer pin; reusable only while both match) and the after side is the same
  command on the final source. No `--all`, no base checkout for routine work. It says how to label
  the before side, that a missing row is not a zero, that a clean tree's targeted report is empty
  (so a cleanup of untouched code uses the supplied candidate report or reports before-metrics as
  unavailable), and that a family member in a file the before report did not measure is
  unmeasured, not new. Rule 12's "re-scan the complete scope" now names the targeted `check` for
  routine work and `--all` for a baseline, so it cannot be read as a whole-repo scan.
- `docs/runbooks/complexity.md`: the same before/after recipe, plus one short paragraph — locally,
  routine work never needs `--all`; it is for a baseline inventory, enrolment in `enforce` and pin
  moves; enforcing CI measures every in-scope file as the backstop.
- `dist/complexity/refactoring-prompt.md` recompiled.

Not changed: the analyzer, CLI flags, policy, CI (enforcing still implies `--all`), the 15 rules,
`AGENTS.md`/template (already targeted and unambiguous) and `architecture.md` §7.12a (already says
"without a second analyzer").

## Dead ends / choices

- Considered a CLI way to measure explicit files for the clean-tree single-function case (a path
  flag, or calling the pinned Lizard directly). Rejected: a new flag for a documentation edge case,
  and direct runner paths are fragile internals. The truthful instruction — use the report that
  named the candidate, or say before-metrics are unavailable — covers it.
- No new test: the change is prose, and the existing tests already hold the printed prompt byte-for
  -byte to the source and the compiled copy, the 15 rules in order, and the no-private-identifier
  rule. A test that the words "detached worktree" are absent would mirror prose, not behaviour.
